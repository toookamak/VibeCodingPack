项目：DogEar · 折耳书签

说明：

========================================
一、设计数据库之前：先搞清楚你要存什么
========================================

不要一上来就画表。先做这三步。

1.1 第一步：从需求中提取"名词"

  把需求描述中的名词全部列出来，每个名词就是一个"实体候选"。

  以 DogEar 为例，需求中出现的名词：
    书签、链接、URL、文件夹、标签、分类、状态、备注、摘要、
    优先级、Docker、小组件、待办、稍后读、导航页、工作台、
    操作日志、同步队列、配置、偏好...

  不是每个名词都需要一张表。
  下一步做筛选。

1.2 第二步：区分"实体"和"属性"

  实体：需要独立存储、有生命周期、会被单独查询或操作的"东西"
  属性：附属于某个实体、不需要独立存在的"信息"

  判断方法：问自己三个问题

    问题 A：这个东西会不会被独立查询？
      "书签"会 → 是实体
      "书签的标题"不会被独立查询（它总是挂在某本书签下）→ 是属性

    问题 B：这个东西会不会独立创建/删除？
      "文件夹"会 → 是实体
      "文件夹的名称"不会独立创建（它随文件夹一起创建）→ 是属性

    问题 C：这个东西和另一个东西是"属于"关系还是"关联"关系？
      "书签的标题属于书签" → 标题是书签的属性
      "书签关联标签" → 标签是独立实体（因为一个标签可以对应多本书签）

  DogEar 的筛选结果：

    实体（需要独立的表）：
      书签（bookmarks）
      文件夹（folders）
      标签（tags）
      操作日志（operation_log）
      同步队列（sync_queue）
      本地配置（local_config）
      AI 偏好（user_preferences）

    属性（不需要独立的表，作为实体表的字段）：
      标题、URL、描述、备注、摘要、封面图、favicon
      状态、优先级、收藏标记
      创建时间、更新时间、同步状态

    边界情况（需要讨论才决定）：
      标签和书签的关系 → 标签是独立实体，通过中间表关联
      文件夹的层级关系 → 文件夹自引用（parent_id），不需要额外的"层级"表

1.3 第三步：确认实体之间的关系

  画出实体之间的关系，每对关系标注类型：

    书签 ──多对一──→ 文件夹
      一本书签属于一个文件夹
      一个文件夹下有多个书签
      实现：bookmarks 表加 folder_id 字段

    书签 ──多对多──→ 标签
      一本书签可以有多个标签
      一个标签可以对应多个书签
      实现：bookmark_tags 中间表（bookmark_id + tag_id）

    文件夹 ──自引用──→ 文件夹
      一个文件夹可以有多个子文件夹
      实现：folders 表加 parent_id 字段指向自己

    操作日志 ──弱引用──→ 书签/文件夹/标签
      日志记录了对某个实体的操作
      但删除实体时日志保留（不级联删除）
      实现：operation_log 表加 target_type + target_id 字段

    同步队列 ──弱引用──→ 书签
      队列项关联某个书签的变更
      书签删除后队列项可能也需要清理
      实现：sync_queue 表加 bookmark_id 字段

  这一步做完，数据库的骨架就出来了。


========================================
二、怎么设计一张表
========================================

2.1 一张表的思考框架

  设计每张表时，按以下顺序思考：

    ① 这张表存什么？（一句话说清）
    ② 每条记录的唯一标识是什么？（主键）
    ③ 核心业务字段有哪些？（直接与需求相关的数据）
    ④ 和哪些表有关系？（外键）
    ⑤ 常见的查询方式是什么？（决定索引）
    ⑥ 记录的生命周期是什么？（什么时候创建、什么时候删除）
    ⑦ 有没有软删除的需要？（标记删除 vs 物理删除）

2.2 字段类型选择的思考过程

  不要凭感觉选类型。每种类型对应一种数据特征：

  数字类：
    整数数量/计数 → INTEGER
    自增主键 → BIGINT（比 INTEGER 更安全，不容易溢出）
    金额/精确小数 → DECIMAL（不要用 FLOAT，有精度问题）
    百分比/0~1 的值 → FLOAT 可以（精度不是关键）

  文字类：
    长度确定且短（如状态码、枚举）→ VARCHAR(20)
    长度不确定但通常不长（如标题、名称）→ VARCHAR(500)（给足余量）
    长度不确定且可能很长（如文章正文、备注）→ TEXT
    结构化的键值数据 → TEXT 存 JSON 字符串（IndexedDB 中可以直接存对象）

  时间类：
    所有时间统一用 TIMESTAMP 或 ISO 8601 字符串
    统一存 UTC 时间，展示时再转时区
    软删除时间 → 可以为 NULL 的 TIMESTAMP

  布尔类：
    标准写法 → BOOLEAN
    IndexedDB 中 → 用 true/false

  枚举类：
    不用数据库原生 ENUM（不好扩展）
    用 VARCHAR 存字符串值（如 'unread', 'reading', 'read'）
    枚举值的合法范围在应用层校验

2.3 什么时候加索引

  不是每个字段都需要索引。索引的规则：

  必须加索引的字段：
    - 主键（自动索引）
    - 外键（所有引用其他表的字段）
    - 频繁出现在 WHERE 条件中的字段
    - 频繁用于排序（ORDER BY）的字段

  不需要加索引的字段：
    - 大文本字段（TEXT 类型，如正文、备注）
    - 很少用于查询条件的字段（如 cover_url）
    - 值高度重复的字段（如只有 true/false 的布尔字段，索引效果很差）

  索引命名规范：
    idx_表名缩写_字段名
    如：idx_bm_status, idx_fol_parent, idx_bt_tag

2.4 设计时的常见错误

  错误 1：把所有东西塞进一张表
    "书签的标签直接存成 JSON 数组在书签表里"
    问题：无法高效地按标签筛选，无法维护标签的元数据（使用次数等）
    正确做法：标签独立建表，用中间表关联

  错误 2：过度拆分
    "书签的标题单独建一张 titles 表"
    问题：标题是书签的属性，不会独立存在
    正确做法：标题就是 bookmarks 表的一个字段

  错误 3：缺少时间字段
    "只建了业务字段，没有 created_at 和 updated_at"
    问题：无法追踪数据的变化历史，同步引擎无法判断增量
    正确做法：每张表至少有 created_at 和 updated_at

  错误 4：用自然键做主键
    "用 URL 做书签的主键"
    问题：URL 可能变化，URL 可能很长导致索引效率低
    正确做法：用自增 ID 做主键，URL 加 UNIQUE 约束

  错误 5：忽略软删除
    "删除就是 DELETE FROM"
    问题：误删无法恢复，关联数据可能产生孤儿记录
    正确做法：加 deleted_at 字段，标记删除


========================================
三、已有数据时如何合理扩展
========================================

这是最关键的场景：你的数据库已经在运行了，
里面有真实数据，现在要加新功能。

3.1 扩展的四种情况

  情况 A：新增字段
    最常见的扩展。
    危险等级：低

    思考过程：
      ① 这个字段是必填的还是可选的？
      ② 旧数据中这个字段应该是什么值？
      ③ 旧数据填默认值合理吗？还是需要特殊处理？

    规则：
      - 如果是可选字段（可以为 NULL）→ 直接加，无风险
      - 如果是必填字段但有合理默认值 → 加字段 + DEFAULT，旧记录自动填充
      - 如果是必填字段且没有合理默认值 → 必须写数据迁移脚本，
        把旧记录补上合理的值，然后再加 NOT NULL 约束

    示例：给书签表加"优先级"字段
      priority VARCHAR(10) NULL DEFAULT NULL
      → 旧记录的 priority 为 NULL，表示"未设置"
      → 应用层对 NULL 和低优先级做同等处理
      → 安全，不需要数据迁移

    示例：给书签表加"必须非空的分类编码"字段
      category_code VARCHAR(20) NOT NULL
      → 旧记录没有这个值，直接加会报错
      → 先加字段，允许 NULL
      → 写迁移脚本：UPDATE bookmarks SET category_code = 'default' WHERE category_code IS NULL
      → 再设 NOT NULL 约束

  情况 B：新增表
    危险等级：最低（不影响已有数据）

    思考过程：
      ① 新表和旧表有什么关系？
      ② 是否需要从旧表迁移数据到新表？
      ③ 旧表是否需要新增字段来引用新表？

    规则：
      - 纯新建、无关联 → 直接建表
      - 需要从旧表迁移数据 → 先建表，再写迁移脚本
      - 旧表需要新增字段引用新表 → 按"情况 A"处理

    示例：新增"AI 偏好"表
      → 独立新表，不影响任何已有数据
      → 直接创建

    示例：新增"书签与标签"中间表
      → 如果之前标签存在 JSON 字段里，需要迁移
      → 先建表，再遍历旧书签，解析 JSON，写入中间表
      → 迁移完成后再考虑删除旧的 JSON 字段

  情况 C：修改已有字段
    危险等级：中到高

    子情况 C1：重命名字段
      风险：旧代码还在用旧字段名，会报错
      正确做法：
        不要直接重命名。
        ① 新增新字段
        ② 迁移旧字段数据到新字段
        ③ 更新所有使用旧字段的代码
        ④ 确认无误后，废弃旧字段（不立即删除）
        ⑤ 下一个大版本再物理删除旧字段

    子情况 C2：修改字段类型
      风险：类型不兼容导致数据丢失或转换错误
      正确做法：
        ① 确认旧数据能否安全转换为新类型
        ② 如能（如 VARCHAR → TEXT）→ 直接改，无风险
        ③ 如不能（如 VARCHAR → INTEGER，且旧值中有非数字）→
           必须先清洗数据，处理不兼容的值，再改类型
        ④ 写迁移脚本，包含数据转换逻辑

    子情况 C3：扩大字段长度
      风险：低
      如 VARCHAR(100) → VARCHAR(500)
      直接改即可，不影响已有数据

    子情况 C4：缩小字段长度
      风险：高
      如 VARCHAR(500) → VARCHAR(100)
      必须先检查是否有数据超过新长度
      如果有 → 必须处理（截断或拒绝变更）

  情况 D：拆分或合并表
    危险等级：最高

    拆分表：
      场景：一张表承载了太多职责，需要拆成两张
      正确做法：
        ① 创建新表
        ② 写迁移脚本：从旧表读数据，分配到新表
        ③ 更新所有读写旧表的代码
        ④ 验证数据完整性
        ⑤ 废弃旧表（不立即删除）

    合并表：
      场景：两张表的数据关联紧密，合并更合理
      正确做法：
        ① 创建合并后的新表
        ② 写迁移脚本：JOIN 两张旧表，写入新表
        ③ 更新代码
        ④ 验证
        ⑤ 废弃旧表

3.2 扩展时的检查清单

  每次扩展数据库时，按此清单逐项检查：

    □ 新增/修改的字段在数据模型文档中有定义吗？
    □ 旧数据如何处理？有迁移脚本吗？
    □ 新字段有默认值吗？旧记录会怎样？
    □ 需要新增索引吗？
    □ 有哪些代码在读这张表？需要更新吗？
    □ 有哪些代码在写这张表？需要更新吗？
    □ 迁移脚本有回滚方案吗？
    □ 迁移后数据完整性如何验证？
    □ 文档更新了吗？版本号更新了吗？


========================================
四、如何验证 AI 设计的表是否合理
========================================

当 AI 给你一个数据库设计方案时，你需要有能力判断它是否靠谱。
以下是验证框架。

4.1 验证维度一：结构合理性

  检查项 1：每张表是否有明确的单一职责？
    合理：bookmarks 表只存书签数据
    不合理：bookmarks 表同时存书签数据和文件夹数据

    验证方法：用一句话描述这张表存什么。
    如果需要用"和""以及"来描述，可能职责过多，需要拆分。

  检查项 2：字段是否属于这张表？
    合理：bookmarks 表有 title、url、folder_id
    不合理：bookmarks 表有 folder_name（文件夹名应该从 folders 表查）

    例外：适度冗余是允许的（如存储 folder_name 做查询优化），
    但必须与主数据源（folders 表的 name 字段）保持同步。

    验证方法：对每个字段问"这个字段的值是由这张表决定的，
    还是由另一张表决定的？"如果由另一张表决定，应该是外键而非直接存储。

  检查项 3：是否正确使用了关系类型？
    一对多：是否在"多"的一方加了外键？
    多对多：是否建了中间表？
    自引用：是否用 parent_id 实现？

    验证方法：画出实体关系图，检查每条关系的实现方式。

4.2 验证维度二：扩展性

  检查项 4：新增字段是否方便？
    好的信号：新功能需要的数据可以作为新字段加到已有表中，
    或者作为新表通过外键关联
    坏的信号：需要修改已有字段的含义，或者需要大量迁移才能支持新功能

    验证方法：假设未来需要"给书签加一个项目关联功能"，
    看现有结构是否只需要加一个 project_id 字段就能支持。
    如果可以 → 扩展性好。
    如果需要重构整张表 → 扩展性差。

  检查项 5：枚举值是否容易扩展？
    好的做法：用 VARCHAR 存字符串枚举值，新增值只需加一个字符串
    坏的做法：用数据库原生 ENUM 类型，新增值需要 ALTER TABLE

    验证方法：看所有枚举字段的类型定义。

  检查项 6：JSON 字段的使用是否合理？
    合理使用：存储灵活的、不需要单独查询的配置数据
    不合理使用：存储需要筛选、排序、聚合的业务数据

    验证方法：对每个 JSON 字段问"我需要按这个字段里的某个值来筛选吗？"
    如果是 → 应该拆成独立字段或独立表
    如果否 → JSON 是合理的

4.3 验证维度三：维护性

  检查项 7：命名是否一致？
    同一个概念在所有表中是否用了相同的名称？
    例如：如果书签的 ID 叫 id，其他表引用它时是否统一叫 bookmark_id？
    不要出现：一个表叫 bookmark_id，另一个表叫 bm_id，第三个表叫 ref_id

    验证方法：列出所有外键字段，检查命名一致性。

  检查项 8：是否有软删除？
    所有需要删除保护的表是否都有 deleted_at 字段？
    不需要软删除的表：纯日志类（operation_log）、配置类（local_config）

    验法方法：列出所有表，逐张检查是否有删除需求。

  检查项 9：时间字段是否完整？
    每张表是否至少有 created_at 和 updated_at？
    是否有需要但缺失的时间字段（如 last_visited_at、last_synced_at）？

    验证方法：逐张表检查。

  检查项 10：索引是否覆盖了常见查询？
    AI 设计时应该说明每张表的常见查询。
    检查每个查询的 WHERE 条件和 ORDER BY 字段是否有对应索引。

    验证方法：列出查询 → 对照索引列表。

4.4 验证维度四：与 Raindrop 的兼容性

  本项目特殊性：数据需要与 Raindrop 双向同步。

  检查项 11：是否有 Raindrop 的 ID 字段？
    每张与 Raindrop 同步的表是否都有 raindrop_id 字段？
    本地 ID 和 Raindrop ID 是否分开管理？

    验证方法：检查 bookmarks 和 folders 表是否有 raindrop_id。

  检查项 12：是否有同步状态字段？
    与 Raindrop 同步的表是否有 sync_status 字段？
    是否有 local_version 和 remote_version？

    验证方法：检查需要同步的表。

  检查项 13：标签结构是否兼容？
    Raindrop 的标签是数组形式。
    本地存储是否能无损地和 Raindrop 的标签格式互相转换？

    验证方法：确认 bookmark_tags 中间表的设计
    能否完整表达 Raindrop 的标签数据。


========================================
五、AI 是否需要在开发中维护数据库文档
========================================

5.1 结论：必须维护

  原因：

    原因 1：文档是约束 AI 的依据
      没有文档，AI 每次接到需求都会重新思考表结构，
      产生不一致的设计。
      有文档，AI 必须基于已有设计做增量修改。

    原因 2：文档是变更审计的依据
      当出了问题（数据损坏、不兼容），可以通过文档追溯：
      "这个字段是什么时候加的？为什么加？迁移脚本在哪？"

    原因 3：文档是跨会话的连续性保障
      AI 的上下文窗口有限，不可能记住所有表结构。
      文档让 AI 在每次新对话中都能快速恢复到准确的项目理解。

5.2 数据库文档应该包含什么

  结构如下：

    第一部分：总览
      - 数据库名称和类型（IndexedDB / SQLite / PostgreSQL 等）
      - 当前版本号
      - 所有表的清单（表名 + 一句话描述 + 记录量级预估）

    第二部分：每张表的完整定义
      - 表名和用途
      - 每个字段的定义（名称、类型、约束、默认值、说明）
      - 索引列表（索引名、字段、用途说明）
      - 关系说明（外键指向、关联表、关系类型）
      - 记录的生命周期（什么时候创建、什么时候删除、软删除策略）

    第三部分：枚举值定义
      - 所有枚举类型的集中定义
      - 每个值的含义、引入版本、是否仍有效

    第四部分：查询模式参考
      - 列出所有常见的查询场景
      - 每个场景对应的表、条件、排序、使用的索引
      - 这是后续验证索引合理性的依据

    第五部分：迁移记录
      - 按时间顺序记录每一次 schema 变更
      - 每条记录包含：版本、日期、原因、变更内容、
        影响范围、迁移脚本（up/down）、数据迁移说明

    第六部分：备份策略
      - 哪些数据需要备份、哪些可以舍弃
      - 导出格式
      - 恢复流程

5.3 如何约束 AI 维护文档

  规则 1：文档优先于代码
    数据模型文档是 schema 的单一事实来源。
    如果文档和代码不一致，以文档为准，代码需要修正。

  规则 2：变更必须先更新文档
    AI 在修改数据库结构之前，必须先在文档中写明：
    - 要改什么
    - 为什么改
    - 怎么迁移旧数据
    文档更新后才能执行变更。

  规则 3：每次 AI 交付数据库相关代码后，人工检查文档
    检查点：
    - 文档是否更新了？
    - 新增的字段/表是否在文档中有完整定义？
    - 迁移记录是否包含了这次变更？
    - 枚举值是否有更新？

  规则 4：版本号必须更新
    每次 schema 变更，文档的版本号必须递增。
    如果版本号没变但表结构变了，说明文档没有被维护。

  规则 5：迁移记录不可省略
    即使是"加一个字段"这样的小变更，也必须有迁移记录。
    没有迁移记录的变更是危险的——你不知道它是什么时候做的、
    做了什么、能不能回滚。


========================================
六、实操：用 DogEar 项目演示完整流程
========================================

下面用一个具体的例子，演示从需求到表设计到验证到文档维护的完整流程。

6.1 场景

  新需求："给书签增加项目关联功能，
  可以把书签和某个项目关联起来，
  方便按项目维度查看和管理书签。"

6.2 第一步：提取名词，识别实体

  需求中的名词：书签、项目、关联

  书签 → 已有实体（bookmarks 表）
  项目 → 新实体？判断：
    - 会不会被独立查询？→ 会（列出所有项目、选择项目）
    - 会不会独立创建/删除？→ 会
    - 结论：是独立实体，需要新表
  关联 → 不是实体，是关系（书签和项目之间的多对一关系）

6.3 第二步：确定关系类型

  一本书签属于一个项目？还是可以属于多个？
  → 假设一本书签只能属于一个项目（更简单，也更合理）
  → 多对一关系：书签 → 项目
  → 实现：bookmarks 表加 project_id 字段

  但如果未来需要一本书签关联多个项目呢？
  → 那就是多对多，需要中间表
  → 现在先按多对一做（简单场景）
  → 如果将来需要多对多，再扩展（情况 B + C）

6.4 第三步：设计 projects 表

  projects 表：
    字段名          类型              约束         默认值    说明
    id              BIGINT            PK, 自增     -        主键
    name            VARCHAR(200)      NOT NULL     -        项目名称
    description     TEXT              NULL         NULL     项目描述
    color           VARCHAR(20)       NULL         NULL     项目颜色标识
    sort_order      INTEGER           NOT NULL     0        排序权重
    created_at      TIMESTAMP         NOT NULL     NOW()    创建时间
    updated_at      TIMESTAMP         NOT NULL     NOW()    更新时间
    deleted_at      TIMESTAMP         NULL         NULL     软删除时间

  索引：
    idx_proj_name     ON (name)                     — 按名称查找
    idx_proj_deleted  ON (deleted_at)               — 软删除查询

6.5 第四步：扩展 bookmarks 表

  bookmarks 表新增字段：
    project_id      BIGINT            FK→projects.id NULL    所属项目

  索引：
    idx_bm_project    ON (project_id)               — 按项目筛选

  这是"情况 A：新增字段"，且是可选字段（可以为 NULL），
  旧数据的 project_id 为 NULL 表示"未关联项目"，
  不需要数据迁移，安全。

6.6 第五步：验证

  结构合理性：
    □ projects 表职责单一（只存项目数据）→ 合理
    □ project_id 作为外键在 bookmarks 表中 → 合理
    □ 未关联项目的书签 project_id = NULL → 合理

  扩展性：
    □ 如果将来需要多对多，可以新增 bookmark_projects 中间表，
      然后废弃 project_id 字段 → 有扩展路径
    □ 新增项目属性（如截止日期、负责人）只需给 projects 表加字段 → 合理

  维护性：
    □ 命名一致：project_id 而非 proj_id → 合理
    □ 有 deleted_at（软删除）→ 合理
    □ 有 created_at 和 updated_at → 合理

  与 Raindrop 的兼容性：
    □ projects 是本地概念，Raindrop 中没有对应 → 不需要 raindrop_id
    □ bookmarks 的同步不受影响（project_id 不同步到 Raindrop）→ 合理

6.7 第六步：更新文档

  在 DATA_MODEL.md 中：
    - 新增 projects 表的完整定义
    - 更新 bookmarks 表的字段列表（新增 project_id）
    - 更新表关系图
    - 新增查询模式："按项目筛选书签"
    - 新增迁移记录 M002

  迁移记录示例：

    迁移编号：M002
    版本：v1.0 → v1.1
    日期：2026-08-22
    原因：新增项目关联功能

    变更内容：
      - 新增 projects 表及索引
      - bookmarks 表新增 project_id 字段及索引

    影响范围：
      - 无破坏性变更
      - 旧书签的 project_id 为 NULL（未关联项目）

    迁移脚本（up）：
      IndexedDB onupgradeneeded version 2:
        创建 projects 表
        打开 bookmarks 对象存储，新增 project_id 索引

    迁移脚本（down）：
      删除 projects 表
      （IndexedDB 不支持删除索引，需要重建 bookmarks 对象存储）

    数据迁移：无

设计表时的思考顺序：
  提取名词 → 区分实体和属性 → 确认关系 → 设计字段 → 设计索引

扩展数据库时的思考顺序：
  属于哪种情况（A/B/C/D）→ 旧数据怎么处理 → 写迁移脚本 → 更新文档

验证 AI 设计时的检查维度：
  结构合理性（4 项）→ 扩展性（3 项）→ 维护性（4 项）→ 兼容性（3 项）

数据库文档必须包含：
  总览 → 表定义 → 枚举值 → 查询模式 → 迁移记录 → 备份策略

约束 AI 的五条规则：
  文档优先于代码
  变更必须先更新文档
  每次交付后人工检查文档
  版本号必须更新
  迁移记录不可省略
