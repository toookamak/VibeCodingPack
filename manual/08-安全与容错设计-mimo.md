## 第一篇：安全设计

安全不是一个功能，而是贯穿整个开发过程的意识。本篇讨论认证授权、输入校验、数据安全等核心安全设计。

### 第一章：认证与授权

#### 1.1 Token 生命周期

Token 是用户身份的数字凭证，管理好 Token 的整个生命周期是认证安全的基础。

**生成**：

- 使用标准的 JWT（JSON Web Token）或 OAuth 2.0 流程
- Access Token 有效期建议 15-30 分钟
- Refresh Token 有效期建议 7-30 天
- Token 中不要存储敏感信息（密码、完整手机号等）

**存储**：

| 存储位置 | 适用场景 | 注意事项 |
|----------|----------|----------|
| HTTP-only Cookie | 传统 Web 应用 | 防 XSS，设置 `SameSite` 和 `Secure` 标志 |
| 内存变量 | SPA 前端应用 | 刷新页面丢失，需要配合 Refresh Token |
| LocalStorage | 不推荐存储 Token | 容易被 XSS 攻击窃取 |

**轮换**：

- Access Token 过期后使用 Refresh Token 换取新 Token
- Refresh Token 使用后立即作废（Rotation 策略）
- 检测到异常登录时，强制所有 Token 失效

**泄露应对**：

1. 立即吊销所有已发放的 Token
2. 通知受影响的用户重新登录
3. 检查泄露原因（日志、数据库、前端代码）
4. 考虑是否需要通知相关方

> **示例——博客平台场景**：用户登录后获得一个 30 分钟的 Access Token 和一个 7 天的 Refresh Token。Access Token 过期后自动用 Refresh Token 换取新 Token，用户无感知。如果检测到同一账号在短时间内从多个城市登录，立即吊销该账号所有 Token 并要求重新验证身份。

#### 1.2 输入校验

所有外部输入都是不可信的——无论是用户表单、URL 参数还是 API 请求体。输入校验是防御攻击的第一道防线。

**XSS 防护**：

XSS（跨站脚本攻击）是指攻击者在页面中注入恶意脚本。

| 防护层级 | 措施 | 说明 |
|----------|------|------|
| 输出编码 | 对动态内容进行 HTML 实体编码 | `<` 转为 `&lt;`，`>` 转为 `&gt;` |
| 内容安全策略 | 设置 CSP 响应头 | 限制可执行的脚本来源 |
| 框架默认转义 | 使用 React/Vue 等框架的默认渲染机制 | 框架会自动转义插值内容 |
| 避免危险 API | 不使用 `dangerouslySetInnerHTML`（除非必须且已做清洗） | 仅在可信内容时使用 |

**注入防护**：

- SQL 查询使用参数化查询或 ORM，禁止拼接 SQL 字符串
- Shell 命令使用转义或专门的库，不要直接拼接用户输入
- NoSQL 查询使用类型校验，防止查询注入

```ts
// ❌ 不好——SQL 注入风险
const query = `SELECT * FROM orders WHERE name = '${userName}'`

// ✅ 好——参数化查询
const query = 'SELECT * FROM orders WHERE name = $1'
const result = await db.query(query, [userName])
```

**数据清洗**：

- 邮箱地址：去除首尾空格，统一小写
- 用户名：限制长度（如 3-50 字符），过滤特殊字符
- 富文本内容：使用白名单策略，只允许安全的 HTML 标签
- 文件名：去除路径分隔符，防止路径穿越

#### 1.3 HTTPS 与 CORS

**HTTPS**：

- 生产环境必须使用 HTTPS，不接受任何例外
- 本地开发环境可以用 HTTP（localhost）
- 配置 HSTS（HTTP Strict Transport Security）头部，强制浏览器使用 HTTPS
- 定期检查证书有效性，使用自动化工具管理证书续期

**CORS（跨域资源共享）**：

CORS 策略控制哪些域名可以访问你的 API。

```ts
// ✅ 严格的 CORS 配置
const corsOptions = {
  origin: 'https://your-app.com',    // 只允许指定域名
  methods: ['GET', 'POST', 'PUT'],   // 只允许必要的 HTTP 方法
  credentials: true,                  // 允许携带凭证
  maxAge: 86400                       // 预检请求缓存 24 小时
}
```

**常见错误**：

| 做法 | 说明 |
|------|------|
| ❌ `origin: '*'` | 允许所有域名访问，安全风险极高 |
| ❌ `methods: '*'` | 允许所有 HTTP 方法，攻击面过大 |
| ✅ 明确指定 origin 和 methods | 最小权限原则，只开放必要的访问 |

### 第二章：数据安全

#### 2.1 敏感配置管理

密钥、Token、数据库连接字符串等敏感信息绝对不能提交到版本控制中。

**规则**：

- 使用 `.env` 文件存放本地开发的环境变量
- `.env` 文件必须加入 `.gitignore`
- 生产环境的密钥通过部署平台的环境变量注入
- 不同环境使用不同的密钥（开发、测试、生产）

**`.env` 文件组织**：

```bash
# .env（本地开发，不提交）
DATABASE_URL=postgresql://localhost:5432/myapp_dev
API_SECRET_KEY=dev-secret-key-local-only
STRIPE_API_KEY=sk_test_xxx

# .env.example（提交到仓库，作为模板）
DATABASE_URL=postgresql://localhost:5432/myapp_dev
API_SECRET_KEY=your-api-secret-key-here
STRIPE_API_KEY=sk_test_or_live_xxx
```

**代码中的引用**：

```ts
// ✅ 通过环境变量引用
const apiKey = process.env.STRIPE_API_KEY

// ❌ 硬编码密钥
const apiKey = 'sk_live_xxxxxxxxxxxxxxxx'
```

#### 2.2 本地数据加密

当应用需要在本地存储敏感数据时（如用户设置、缓存的 API 响应），需要考虑加密。

**分级存储策略**：

| 数据类型 | 存储方式 | 说明 |
|----------|----------|------|
| 用户账号密码 | 不存储，使用认证服务 | 前端永远不存储明文密码 |
| API Token | HTTP-only Cookie 或安全存储 | 浏览器级安全隔离 |
| 用户偏好设置 | 明文存储即可 | 如主题颜色、语言偏好 |
| 业务敏感数据 | 加密后存储 | 如个人地址、支付信息 |

**实现要点**：

- 使用 Web Crypto API 或成熟的加密库（如 `crypto-js`）
- 密钥不能硬编码在代码中，通过环境变量或密钥管理服务获取
- 加密算法优先选择 AES-256-GCM（认证加密，能检测数据篡改）

#### 2.3 Rate Limiting

限速是防止 API 被滥用的基本手段。没有限速的 API 等于没有门锁的房间。

**常见的限速维度**：

| 维度 | 适用场景 | 示例 |
|------|----------|------|
| 每用户 | 防止单个用户滥用 | 每用户每分钟 60 次请求 |
| 每 IP | 防止批量请求攻击 | 每 IP 每分钟 120 次请求 |
| 每端点 | 保护关键接口 | 登录接口每 IP 每分钟 5 次 |
| 全局 | 保护服务整体稳定性 | 总 QPS 不超过 1000 |

**限速响应**：

```json
// 429 Too Many Requests 响应
{
  "error": {
    "code": "RATE_LIMITED",
    "message": "请求过于频繁，请稍后再试",
    "retryAfter": 30
  }
}
```

**关键接口的限速建议**：

| 接口 | 建议限制 | 说明 |
|------|----------|------|
| 登录/注册 | 5 次/分钟/IP | 防止暴力破解 |
| 密码重置 | 3 次/小时/邮箱 | 防止枚举攻击 |
| 文件上传 | 10 次/小时/用户 | 防止存储滥用 |
| 普通查询 | 60 次/分钟/用户 | 保证正常使用的前提下防滥用 |

## 第二篇：容错策略

再健壮的系统也会出错。关键不是"不出错"，而是"出错后怎么办"。本篇讨论错误处理体系和降级方案。

### 第三章：错误处理体系

#### 3.1 全局错误捕获

应用运行时可能出现未捕获的异常和未处理的 Promise 拒绝。如果不处理这些情况，应用会静默崩溃，用户看到的是白屏或无响应。

**未捕获异常**：

```ts
// 捕获所有未处理的同步异常
window.addEventListener('error', (event) => {
  // 记录错误信息
  console.error('未捕获的异常:', event.error)
  // 上报到错误监控服务
  reportError(event.error)
  // 显示友好的错误提示
  showFallbackUI()
})
```

**未处理的 Promise 拒绝**：

```ts
// 捕获所有未处理的 Promise 拒绝
window.addEventListener('unhandledrejection', (event) => {
  console.error('未处理的 Promise 拒绝:', event.reason)
  reportError(event.reason)
  // 阻止默认的控制台报错行为
  event.preventDefault()
})
```

**注意事项**：

- 全局错误捕获是最后的防线，不应替代正常的错误处理
- 记录足够的上下文信息（用户操作、错误堆栈、设备信息）
- 不要在全局处理中暴露敏感数据
- 全局处理后给用户一个可操作的反馈（重试按钮、返回首页等）

#### 3.2 错误分类

不同类型的错误需要不同的处理策略。分类是正确处理的前提。

| 错误类别 | 说明 | 示例 | 处理方式 |
|----------|------|------|----------|
| 业务错误 | 用户操作不符合业务规则 | 余额不足、库存不够 | 提示用户具体原因，引导修正操作 |
| 系统错误 | 应用内部异常 | 空指针、类型错误、逻辑错误 | 记录日志、上报监控、提示用户重试 |
| 外部依赖错误 | 第三方服务不可用 | API 超时、支付服务异常 | 重试、降级、提示用户稍后重试 |
| 网络错误 | 网络连接问题 | 断网、请求超时 | 检测网络状态、缓存优先、离线提示 |

**错误码设计**：

```ts
// 前缀标识错误来源
enum ErrorCode {
  // 业务错误（BIZ 前缀）
  BIZ_INSUFFICIENT_BALANCE = 'BIZ_001',
  BIZ_PRODUCT_OUT_OF_STOCK = 'BIZ_002',
  
  // 系统错误（SYS 前缀）
  SYS_DATABASE_ERROR = 'SYS_001',
  SYS_INTERNAL_ERROR = 'SYS_002',
  
  // 外部依赖错误（EXT 前缀）
  EXT_API_TIMEOUT = 'EXT_001',
  EXT_PAYMENT_UNAVAILABLE = 'EXT_002',
  
  // 网络错误（NET 前缀）
  NET_OFFLINE = 'NET_001',
  NET_REQUEST_TIMEOUT = 'NET_002',
}
```

#### 3.3 三层处理模型

推荐采用"数据层抛出 → Hooks 层捕获 → 组件层展示"的三层错误处理模型。每一层只负责自己该做的事。

**数据层——抛出结构化错误**：

数据层不处理错误，只负责识别错误并抛出结构化的错误信息。

```ts
// lib/db/orders.ts
export async function getOrders(filter?: OrderFilter): Promise<Order[]> {
  try {
    const result = await db.query('SELECT * FROM orders', filter)
    return result.rows
  } catch (error) {
    // 识别错误类型，抛出结构化错误
    if (error.code === 'ECONNREFUSED') {
      throw new AppError(ErrorCode.SYS_DATABASE_ERROR, '数据库连接失败', { cause: error })
    }
    throw new AppError(ErrorCode.SYS_INTERNAL_ERROR, '查询订单失败', { cause: error })
  }
}
```

**Hooks 层——捕获并转换**：

Hooks 层负责调用数据层、捕获错误、转换为 UI 可用的状态。

```ts
// hooks/useOrders.ts
export function useOrders(filter?: OrderFilter) {
  const [orders, setOrders] = useState<Order[]>([])
  const [error, setError] = useState<AppError | null>(null)
  const [loading, setLoading] = useState(false)

  const fetchOrders = useCallback(async () => {
    setLoading(true)
    setError(null)
    try {
      const data = await getOrders(filter)
      setOrders(data)
    } catch (err) {
      if (err instanceof AppError) {
        setError(err)
      } else {
        setError(new AppError(ErrorCode.SYS_INTERNAL_ERROR, '加载订单失败'))
      }
    } finally {
      setLoading(false)
    }
  }, [filter])

  return { orders, error, loading, refetch: fetchOrders }
}
```

**组件层——展示错误信息**：

组件层只负责根据错误状态展示对应的 UI。

```tsx
// features/orders/components/OrderList.tsx
function OrderList() {
  const { orders, error, loading, refetch } = useOrders()

  if (loading) return <OrderListSkeleton />
  if (error) {
    return (
      <ErrorState
        message={error.userMessage}
        onRetry={refetch}
        showDetails={error.isSystemError}
      />
    )
  }
  return <OrderTable orders={orders} />
}
```

### 第四章：降级方案

当系统某个部分出问题时，如何保证核心功能仍能使用？这就是降级方案要解决的问题。

#### 4.1 外部服务不可用降级

应用通常依赖多个外部服务（支付 API、地图服务、搜索服务等）。任何一个不可用都不应导致整个应用崩溃。

**降级策略**：

| 外部服务 | 降级策略 | 影响 |
|----------|----------|------|
| 支付服务 | 展示"支付暂时不可用"，记录订单待支付状态，稍后重试 | 用户无法完成支付，但订单保留 |
| 搜索服务 | 切换到数据库模糊查询 | 搜索结果质量下降，但功能可用 |
| 推荐服务 | 展示默认推荐列表（缓存或静态数据） | 推荐不个性化，但不空白 |
| 短信服务 | 切换到备用通道，或延迟发送 | 可能有延迟，但不丢失 |
| CDN | 回源到主服务器 | 速度变慢，但内容正常 |

**实现模式**：

```ts
// 外部服务调用的降级包装
async function fetchWithFallback<T>(
  primary: () => Promise<T>,
  fallback: () => Promise<T>,
  options?: { timeout?: number }
): Promise<T> {
  try {
    // 使用 Promise.race 实现超时控制
    const result = await Promise.race([
      primary(),
      createTimeoutError(options?.timeout ?? 5000)
    ])
    return result
  } catch (error) {
    console.warn('主服务不可用，使用降级方案:', error)
    return fallback()
  }
}

// 使用示例
const products = await fetchWithFallback(
  () => searchService.search(query),         // 主服务：外部搜索 API
  () => db.fuzzySearch(query),               // 降级：数据库模糊查询
  { timeout: 3000 }
)
```

#### 4.2 离线场景

网络不可用时（地铁、飞机、信号差的区域），应用应该尽可能保持可用。

**功能分级**：

| 优先级 | 功能 | 离线策略 |
|--------|------|----------|
| P0 核心功能 | 已缓存数据的查看、本地编辑 | 完全可用，数据暂存本地 |
| P1 重要功能 | 已缓存页面的浏览 | 使用 Service Worker 缓存策略 |
| P2 辅助功能 | 搜索、推荐、新内容加载 | 暂时不可用，显示"离线提示" |

**离线检测与通知**：

```ts
// 监听网络状态变化
window.addEventListener('online', () => {
  showToast('网络已恢复')
  // 自动同步离线期间的本地变更
  syncOfflineChanges()
})

window.addEventListener('offline', () => {
  showToast('网络已断开，部分功能暂时不可用')
})
```

**离线数据同步**：

1. 用户在离线状态下操作（如编辑文章），数据暂存到本地队列
2. 网络恢复后，自动将队列中的变更同步到服务端
3. 同步时检测冲突（本地和远端都有修改），提示用户解决

#### 4.3 数据损坏恢复

数据损坏可能由多种原因导致：写入中断、存储介质故障、程序 bug 覆盖错误数据。

**预防措施**：

- 写入操作使用事务（Transaction），确保原子性
- 重要数据变更前做备份（写入新位置 → 验证 → 删除旧位置）
- 数据库使用 WAL（Write-Ahead Logging）模式

**恢复路径**：

```
数据损坏检测
    │
    ├─ 1. 自动恢复
    │   ├─ 从 WAL 日志恢复到最近一致状态
    │   ├─ 从本地备份副本恢复
    │   └─ 从服务端重新同步
    │
    ├─ 2. 手动恢复
    │   ├─ 提供数据修复工具（如"重新同步所有数据"）
    │   └─ 提供数据导出功能，让用户手动备份
    │
    └─ 3. 降级使用
        ├─ 保留可读的数据，标记损坏部分
        └─ 允许用户查看未损坏的数据并手动修复
```

**恢复操作的用户体验**：

- 检测到数据异常时，主动提示用户而非静默失败
- 提供"一键修复"按钮，自动执行恢复流程
- 恢复过程中展示进度，不要让用户觉得应用卡死
- 恢复完成后明确告知结果

## 第三篇：AI 安全

AI 生成的代码可能包含安全漏洞。这些漏洞不是 AI 故意为之，而是因为 AI 在生成代码时优先考虑功能实现，可能忽略安全细节。本篇提供识别和防范这些漏洞的方法。

### 第五章：AI 生成代码安全

#### 5.1 常见漏洞类型

AI 生成的代码中，以下安全漏洞出现频率较高：

| 漏洞类型 | 说明 | 危害等级 | 常见场景 |
|----------|------|----------|----------|
| 硬编码密钥 | API Key、数据库密码直接写在代码中 | 🔴 高 | 数据库连接配置、API 调用 |
| SQL 注入 | 字符串拼接 SQL 查询 | 🔴 高 | 数据查询、数据搜索 |
| XSS 漏洞 | 未转义的用户输入直接渲染到页面 | 🔴 高 | 评论区、富文本展示、搜索结果 |
| 不安全的依赖 | 使用有已知漏洞的第三方库 | 🟡 中 | 引入新依赖时未检查安全公告 |
| 缺少输入校验 | 未验证用户输入的长度、格式、类型 | 🟡 中 | 表单提交、API 接口 |
| 不安全的随机数 | 使用 `Math.random()` 生成安全相关的值 | 🟡 中 | Token 生成、验证码 |
| 信息泄露 | 错误信息中包含敏感的内部细节 | 🟡 中 | 错误处理、日志输出 |
| 缺少 Rate Limiting | API 接口无访问频率限制 | 🟡 中 | 所有对外接口 |
| 不安全的反序列化 | 直接解析不受信任的 JSON/XML 数据 | 🟠 中高 | API 请求处理 |
| 路径穿越 | 文件路径未校验，允许访问系统文件 | 🔴 高 | 文件下载、文件预览 |

#### 5.2 防范清单

以下清单可直接用于每次接收 AI 生成代码后的安全检查：

**必查项（每次都需要检查）**：

- [ ] 代码中是否有硬编码的密钥、Token、密码？
- [ ] SQL 查询是否使用了参数化查询或 ORM？
- [ ] 用户输入是否经过校验和清洗？
- [ ] 动态内容渲染时是否做了输出编码？
- [ ] 文件路径是否做了校验，防止路径穿越？
- [ ] 密码和敏感信息是否使用了安全的哈希/加密算法？
- [ ] API 接口是否配置了 Rate Limiting？

**必查项（涉及特定功能时）**：

- [ ] 涉及认证：Token 是否有合理的过期时间？是否在安全的位置存储？
- [ ] 涉及支付：金额是否在后端验证？是否防止了金额篡改？
- [ ] 涉及文件上传：是否限制了文件类型和大小？是否扫描了文件内容？
- [ ] 涉及用户数据：是否有权限校验？是否遵守了数据最小化原则？
- [ ] 涉及随机数：安全相关场景是否使用了 `crypto.randomBytes()` 而非 `Math.random()`？
- [ ] 涉及第三方 API：密钥是否通过环境变量注入？是否处理了 API 超时和错误？
- [ ] 涉及 WebSocket：是否验证了连接来源？是否有心跳和断线重连？
- [ ] 涉及邮件发送：是否做了发送频率限制？邮件内容是否防止了邮件头注入？

**可选增强项（按需检查）**：

- [ ] 错误信息是否避免暴露内部实现细节（文件路径、数据库结构等）？
- [ ] 日志中是否排除了敏感数据（密码、Token、完整手机号等）？
- [ ] CORS 策略是否使用了白名单？
- [ ] Content-Security-Policy 是否已配置？
- [ ] 依赖项是否有已知漏洞（运行 `npm audit`）？

#### 5.3 安全审查流程

每次接收 AI 生成的代码后，按以下步骤进行安全审查：

```
AI 生成代码
    │
    ▼
┌─────────────────────────────────┐
│  第一步：快速扫描（2-3 分钟）     │
│  • 扫描硬编码的密钥和 Token      │
│  • 检查 SQL 查询是否参数化       │
│  • 检查是否有直接渲染用户输入     │
│  • 检查是否有危险的 API 调用     │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  第二步：功能安全检查（5-10 分钟）│
│  • 对照防范清单逐项检查           │
│  • 关注与本功能相关的特定检查项   │
│  • 检查错误处理是否合理           │
│  • 检查是否有信息泄露风险         │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  第三步：修复与验证（按需）       │
│  • 发现问题后明确描述给 AI 修复   │
│  • 修复后再次检查确认             │
│  • 记录发现的问题，积累经验       │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  第四步：提交前最终确认           │
│  • 再次快速扫描是否有遗漏         │
│  • 运行安全相关的测试（如有）     │
│  • 运行 npm audit 检查依赖       │
└─────────────────────────────────┘
```

**向 AI 反馈安全问题的模板**：

当发现 AI 生成的代码存在安全问题时，使用以下方式反馈：

```

```

## 全文总结

安全与容错不是"锦上添花"，而是"地基"。没有安全设计的应用，功能再多也是空中楼阁。没有容错策略的系统，正常运行时看不出问题，一旦出错就全面崩溃。

**核心理念**：

1. **安全是持续的过程**，不是一次性工作——每次代码变更都可能引入新的安全风险
2. **假设所有输入都不可信**——永远不要信任用户输入、第三方数据、甚至自己的 API 返回值
3. **出错是正常的**——关键是出错后系统仍然可用，用户仍然能得到反馈
4. **AI 生成的代码需要审查**——AI 是生产力工具，不是安全审计工具
