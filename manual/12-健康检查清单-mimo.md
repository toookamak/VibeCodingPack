# 健康检查清单

- **日期**：2026-08-21
- **版本**：v1.0
- **适用范围**：适用于个人开发者与 AI 协作的中小型项目，覆盖从需求分析到上线运维的全流程质量把关。本文使用通用场景示例，不绑定特定项目。

---

## 第一篇：检查维度总览

在深入每个维度的细节之前，先建立全局视角。十个检查维度分别对应项目质量的不同切面，理解它们的定位和适用时机，才能在正确的阶段做正确的检查。

### 第一章：十个检查维度

#### 1.1 维度总览表

| # | 维度 | 适用场景 | 检查频率 | 严重级别 |
|---|------|----------|----------|----------|
| 1 | AI 交付检查 | AI 生成或修改代码后 | 每次 AI 交付 | 高——AI 产出的代码若不检查，问题会快速累积 |
| 2 | 代码审查 | 功能开发完成、合并前 | 每次提交或合并前 | 高——代码质量的最后防线 |
| 3 | 功能验收 | 功能开发完成后 | 每个功能完成时 | 高——功能是否符合预期的直接验证 |
| 4 | 体验验收 | UI/UX 变更后 | 每次界面变更 | 中——影响用户满意度但通常不阻断流程 |
| 5 | 数据库扩展 | 新增字段、表或索引时 | 每次数据库变更 | 高——数据库变更影响面广、回滚成本高 |
| 6 | 安全检查 | 涉及输入、认证、API 时 | 每次安全相关变更 + 定期审计 | 高——安全漏洞可能造成不可逆损害 |
| 7 | 依赖引入检查 | 引入或升级第三方依赖时 | 每次依赖变更 | 中——依赖问题可能延迟暴露 |
| 8 | 重构检查 | 代码结构调整时 | 每次重构操作 | 中——重构不当会引入回归缺陷 |
| 9 | 架构健康检查 | 项目规模扩大或里程碑节点 | 定期（每 2-4 周） | 中——架构问题随时间逐渐恶化 |
| 10 | 项目可恢复性 | 项目全生命周期 | 定期（每月） | 高——灾难恢复能力决定项目韧性 |

#### 1.2 严重级别定义

| 级别 | 含义 | 处理要求 |
|------|------|----------|
| P0 — 阻断 | 功能无法运行、数据可能丢失、存在安全漏洞 | 必须立即修复，阻断后续流程 |
| P1 — 严重 | 功能异常但有临时绕行方案、性能严重不达标 | 当前迭代内修复 |
| P2 — 一般 | 代码质量不佳、体验有瑕疵、技术债累积 | 排入计划，择机修复 |
| P3 — 低优 | 风格不统一、文档缺失、可读性可优化 | 有空时处理 |

#### 1.3 维度之间的关系

十个维度并非独立存在，它们之间有明确的依赖和互补关系：

- **AI 交付检查 → 代码审查**：AI 交付检查是代码审查的前置过滤，先由 AI 交付检查扫掉明显问题，再进入人工代码审查。
- **代码审查 → 功能验收**：代码审查确保实现质量，功能验收验证业务正确性。
- **数据库扩展检查 → 功能验收**：数据库变更必须先完成，功能验收才能验证数据流的正确性。
- **安全检查贯穿所有维度**：安全不是独立阶段，而是每个环节都需要关注的切面。
- **架构健康检查 → 重构检查**：架构健康检查发现结构性问题，重构检查确保修复过程不引入新问题。
- **项目可恢复性是兜底保障**：即使前九个维度都出了问题，项目可恢复性确保可以从容应对。

## 第二篇：详细检查清单

本篇逐维度展开，每个维度给出具体、可操作的检查项。建议根据当前阶段选择对应维度逐项核对。

### 第二章：AI 交付检查

AI 生成或修改代码后，必须在合并到项目代码库之前完成以下检查。AI 的产出速度很快，但质量波动也大——这道检查是防止"批量引入隐患"的第一道关卡。

#### 2.1 结构检查

| 检查项 | 通过标准 | 常见问题 |
|--------|----------|----------|
| 文件是否超过 300 行 | 单文件含注释和空行不超过 300 行 | AI 倾向于把所有逻辑写在一个文件里 |
| 是否遵守单一职责 | 每个文件/函数能用一句话描述职责 | 一个函数里既有数据获取又有格式化 |
| 文件位置是否正确 | 按功能模块组织，而非按技术角色 | AI 常把组件扔到全局 components/ 而非模块内 |
| import 顺序是否正确 | 外部 → 组件 → 业务 → 类型 → 样式 | import 顺序混乱或交叉引入 |
| 是否有冗余文件 | 没有多余的空文件或重复文件 | AI 有时会生成 .bak 或临时文件 |

#### 2.2 质量检查

| 检查项 | 通过标准 | 常见问题 |
|--------|----------|----------|
| 是否使用 any 类型 | 禁止 any，用 unknown 或具体类型 | AI 遇到复杂类型时倾向用 any 绕过 |
| 函数参数和返回值是否有类型 | 所有函数都有明确的类型定义 | 箭头函数或回调中遗漏类型 |
| 组件是否定义了 Props 类型 | 所有组件都有 interface/type 定义 | AI 有时用内联解构而不定义类型 |
| 命名是否清晰 | 变量/函数名能表达意图 | AI 喜欢用 `data`、`result`、`temp` 等泛化名 |
| 是否有硬编码的魔法值 | 常量用 UPPER_SNAKE_CASE 命名 | `setTimeout(..., 3000)` 这类散落的数字 |

#### 2.3 依赖检查

| 检查项 | 通过标准 | 常见问题 |
|--------|----------|----------|
| 是否引入了不必要的新依赖 | 能用现有依赖或原生方案解决的不引入新依赖 | AI 倾向于引入库来解决简单问题 |
| 新依赖的体积是否合理 | 打包后增量不超过 50KB（特殊工具类除外） | 为了解决一个小问题引入巨型库 |
| 依赖是否有活跃维护 | 6 个月内有更新，issue 有回复 | 引入了已废弃或长期无人维护的库 |
| 是否引入了重复功能的依赖 | 同一功能不引入多个库 | 项目中已有日期处理库又引入新的 |

#### 2.4 文档检查

| 检查项 | 通过标准 | 常见问题 |
|--------|----------|----------|
| 复杂逻辑是否有注释 | 解释"为什么"而非"做了什么" | AI 生成的代码往往缺少必要注释 |
| TODO 是否标注 | 待完成的工作用 TODO 注释标记 | AI 可能留下未完成的实现 |
| 公共 API 是否有 JSDoc | lib/ 层的函数有参数和返回值说明 | 导出的函数没有文档说明 |
| 变更日志是否更新 | 新增/修改/删除的变更记录到 CHANGELOG | 功能变更了但没有记录 |

### 第三章：代码审查清单

代码审查是将代码合并到主分支前的质量关卡。审查不是为了找 bug（那是测试的事），而是确保代码的可维护性、可读性和一致性。

#### 3.1 结构维度

| 检查项 | 说明 |
|--------|------|
| 文件是否遵守 300 行上限 | 超过则需要拆分 |
| 模块边界是否清晰 | 模块之间通过明确的接口交互，不直接访问内部实现 |
| 依赖方向是否正确 | 上层可以依赖下层，下层不能依赖上层 |
| 目录结构是否符合项目约定 | 按功能模块组织，而非按技术角色 |
| 是否有重复代码 | 同一逻辑出现两次以上应提取为公共函数 |

#### 3.2 边界维度

| 检查项 | 说明 |
|--------|------|
| 函数是否有合理的入参校验 | 不信任外部输入，对参数进行基本校验 |
| 异常处理是否完善 | API 调用、数据库操作等有 try-catch 和降级方案 |
| 边界条件是否处理 | 空数组、null、undefined、空字符串等边界场景 |
| 并发/异步是否正确处理 | Promise 链是否正确 await，是否有竞态条件 |
| 资源是否正确释放 | 事件监听器、定时器、连接等在组件卸载时清理 |

#### 3.3 依赖维度

| 检查项 | 说明 |
|--------|------|
| 是否引入了新依赖 | 新依赖需要说明必要性 |
| 现有依赖是否有版本变更 | 版本升级是否经过验证 |
| 是否有未使用的依赖 | package.json 中声明但代码中未引用的依赖 |
| 锁文件是否同步 | package-lock.json 或 yarn.lock 与 package.json 一致 |

#### 3.4 接口维度

| 检查项 | 说明 |
|--------|------|
| API 接口是否有明确的请求/响应类型 | 前后端对数据结构有统一的类型定义 |
| 组件的 Props 是否有默认值 | 可选参数有合理的默认行为 |
| 模块导出是否最小化 | 只导出必要的接口，内部实现不暴露 |
| 命名是否与项目现有命名一致 | 同一概念在整个项目中使用相同的名字 |

### 第四章：功能验收清单

功能验收的核心是验证"开发的功能是否符合预期"。使用"操作 + 预期结果"的模板格式，逐项核对。

#### 4.1 验收模板

每个功能验收时，按以下格式记录：

```markdown
#### 功能名称：[功能描述]

**前置条件**：[需要满足的前提条件]

| # | 操作步骤 | 预期结果 | 实际结果 | 状态 |
|---|----------|----------|----------|------|
| 1 | [具体操作] | [预期行为] | [实际行为] | ✅/❌ |
| 2 | ... | ... | ... | ... |
```

#### 4.2 通用验收场景

以下是所有功能都需要覆盖的基础验收场景：

| 场景类型 | 检查项 | 说明 |
|----------|--------|------|
| 正常流程 | 核心操作能完成 | 从开始到结束的完整路径 |
| 输入校验 | 无效输入有提示 | 空值、超长、特殊字符、格式错误 |
| 边界条件 | 极端数据能处理 | 0 条数据、1 条数据、大量数据 |
| 状态切换 | 状态流转正确 | 如订单从待处理→处理中→已完成 |
| 并发操作 | 快速操作不崩溃 | 快速点击、重复提交 |
| 数据持久化 | 刷新后数据不丢失 | 页面刷新、重新打开后数据正确 |

#### 4.3 博客平台场景示例

以博客平台的"文章发布"功能为例：

```markdown
#### 功能名称：文章发布

**前置条件**：用户已登录

| # | 操作步骤 | 预期结果 | 实际结果 | 状态 |
|---|----------|----------|----------|------|
| 1 | 输入标题和内容，点击发布 | 文章创建成功，跳转到文章详情页 | | |
| 2 | 标题为空，点击发布 | 提示"标题不能为空"，不提交 | | |
| 3 | 标题超过 200 字符，点击发布 | 提示"标题不能超过 200 字符" | | |
| 4 | 内容为空，点击发布 | 提示"内容不能为空"，不提交 | | |
| 5 | 发布后刷新页面 | 文章仍然存在，内容正确 | | |
| 6 | 连续快速点击发布按钮 | 只创建一篇文章，不重复提交 | | |
| 7 | 离线状态下点击发布 | 提示网络错误，数据不丢失（草稿保留） | | |
```

### 第五章：体验验收清单

功能验收关注"能不能用"，体验验收关注"好不好用"。以下是体验层面的关键检查项。

#### 5.1 反馈机制

| 检查项 | 通过标准 |
|--------|----------|
| 操作后是否有即时反馈 | 点击按钮后有加载状态、提交后有成功/失败提示 |
| 加载状态是否清晰 | 列表加载、表单提交、文件上传等有明确的加载指示 |
| 操作结果是否有通知 | 创建/修改/删除等操作完成后有 toast 或提示 |
| 长时间操作是否有进度 | 批量操作、文件上传等有进度展示 |

#### 5.2 空状态

| 检查项 | 通过标准 |
|--------|----------|
| 列表为空时是否有提示 | 显示"暂无数据"而非空白页面 |
| 搜索无结果时是否有提示 | 显示"未找到匹配的结果"而非空白 |
| 空状态是否有引导操作 | 提供"新建""导入"等操作入口 |

#### 5.3 错误状态

| 检查项 | 通过标准 |
|--------|----------|
| 网络错误是否有友好提示 | 显示"网络连接失败"而非控制台报错 |
| 404 页面是否有引导 | 提供返回首页或上一页的入口 |
| 权限不足是否有提示 | 无权限时显示明确提示而非空白或报错 |
| 表单校验错误是否定位到字段 | 错误信息显示在对应字段旁边 |

#### 5.4 快捷键与导航

| 检查项 | 通过标准 |
|--------|----------|
| 核心操作是否有快捷键 | 列表页的搜索、新建等常用操作支持键盘快捷键 |
| Tab 键是否能遍历表单 | 表单中的字段可以通过 Tab 键依次切换 |
| 页面标题是否正确 | 每个页面的浏览器标签页标题准确描述当前页面 |
| 面包屑/返回路径是否清晰 | 用户知道如何返回上一级 |

### 第六章：数据库扩展检查

数据库变更是高风险操作——一旦上线，回滚成本极高。新增字段、表、索引前必须逐项核对。

#### 6.1 新字段检查

| 检查项 | 说明 |
|--------|------|
| 字段命名是否与现有风格一致 | 已有字段用 `created_at`，新字段不要用 `createTime` |
| 字段类型是否合理 | 金额用 decimal 而非 float，状态用 enum 而非自由文本 |
| 默认值是否设置 | 新增字段必须有默认值，避免现有数据出现 null |
| 是否允许 null | 明确字段是否可空，不可空字段提供合理默认值 |
| 字段注释是否添加 | 数据库层面的字段说明，方便后续维护 |

#### 6.2 旧数据兼容

| 检查项 | 说明 |
|--------|------|
| 现有数据是否能正确读取 | 新字段不影响已有数据的查询和展示 |
| 数据迁移脚本是否编写 | 需要回填数据的场景必须有迁移脚本 |
| 迁移脚本是否可重复执行 | 使用 `IF NOT EXISTS` 等幂等操作 |
| 回滚方案是否明确 | 如果新字段有问题，如何恢复到之前的状态 |

#### 6.3 索引检查

| 检查项 | 说明 |
|--------|------|
| 新查询条件是否有索引 | 频繁用于 WHERE、ORDER BY 的字段需要索引 |
| 索引是否过多 | 每个表的索引不超过 5-6 个，过多会影响写入性能 |
| 复合索引的字段顺序 | 选择性高的字段放前面 |
| 是否有重复索引 | 新索引不与已有索引功能重叠 |

#### 6.4 迁移检查

| 检查项 | 说明 |
|--------|------|
| 迁移脚本是否在测试环境验证 | 先在测试环境执行，确认无误再上生产 |
| 迁移脚本是否有超时保护 | 大表迁移需要分批执行，避免锁表过久 |
| 迁移失败是否有回滚方案 | 每个迁移脚本都应有对应的回滚脚本 |
| 迁移后是否验证数据完整性 | 执行后检查关键数据的正确性 |

### 第七章：安全检查

安全问题的特点是平时不暴露，一旦暴露就可能造成不可逆损害。以下检查项覆盖最常见的安全风险点。

#### 7.1 输入校验

| 检查项 | 说明 | 严重级别 |
|--------|------|----------|
| 用户输入是否在前端和后端都校验 | 前端校验提升体验，后端校验保障安全 | P0 |
| SQL 查询是否使用参数化 | 禁止字符串拼接 SQL，使用参数化查询或 ORM | P0 |
| XSS 防护是否到位 | 用户输入的内容在展示时是否做了转义 | P0 |
| 文件上传是否校验类型和大小 | 限制上传文件的类型、大小，不做这个限制可能导致服务器被攻破 | P1 |
| 路径遍历是否防护 | 文件操作是否限制在指定目录内 | P0 |

#### 7.2 硬编码检查

| 检查项 | 说明 | 严重级别 |
|--------|------|----------|
| 代码中是否有明文密码或密钥 | 所有密钥、令牌等敏感信息必须在环境变量中 | P0 |
| API 地址是否硬编码 | 不同环境的 API 地址应通过配置切换 | P1 |
| 敏感配置是否在版本控制中 | .env 文件应加入 .gitignore | P0 |
| 测试数据是否包含真实用户信息 | 测试数据应使用虚构数据 | P1 |

#### 7.3 API 认证与授权

| 检查项 | 说明 | 严重级别 |
|--------|------|----------|
| 所有 API 是否有认证保护 | 未认证用户不能访问需要认证的接口 | P0 |
| Token 是否有有效期 | 长期有效的 Token 应有刷新机制 | P1 |
| 权限检查是否在服务端 | 不能只在前端做权限控制，后端必须二次校验 | P0 |
| 错误信息是否泄露内部细节 | 401/403/500 等错误不返回堆栈信息或数据库结构 | P1 |
| CORS 配置是否合理 | 不允许 `*` 通配，限制为可信域名 | P1 |

#### 7.4 传输安全

| 检查项 | 说明 | 严重级别 |
|--------|------|----------|
| 是否使用 HTTPS | 生产环境必须全站 HTTPS | P0 |
| 敏感数据是否加密传输 | 密码、令牌等不在 URL 参数中传递 | P0 |
| Cookie 是否设置 Secure 和 HttpOnly | 防止 XSS 窃取 Cookie | P1 |

### 第八章：依赖引入检查

每个第三方依赖都是项目的一份"外部基因"——引入前必须评估，引入后持续监控。

#### 8.1 必要性评估

| 检查项 | 说明 |
|--------|------|
| 原生方案能否解决 | 先用原生 API 或已有依赖尝试，确认确实需要新依赖 |
| 项目的其他模块是否已有同类功能 | 搜索项目中是否已有类似的工具函数或库 |
| 是否可以自己实现 | 如果所需功能只有 20-30 行代码，自己实现可能比引入依赖更可控 |
| 引入的真正原因是什么 | 是"确实需要"还是"自己写太麻烦"？后者不是好理由 |

#### 8.2 体积影响

| 检查项 | 说明 |
|--------|------|
| 安装后磁盘大小 | 通过 `npm ls <package>` 查看 |
| 打包后对应用体积的影响 | 通过构建工具的分析功能查看增量 |
| 间接依赖的数量 | 一个库可能拉入数十个间接依赖 |
| 是否支持按需引入 | 如果只用了库的 10% 功能，是否有 tree-shaking 支持 |

#### 8.3 维护状态

| 检查项 | 说明 |
|--------|------|
| 最近更新时间 | 超过 1 年未更新的库需要谨慎 |
| GitHub star 和 issue 活跃度 | 是否有社区支持 |
| 周下载量 | 下载量过低可能意味着即将被废弃 |
| 文档质量 | 文档是否完整、是否有使用示例 |
| 许可证类型 | 是否与项目许可证兼容 |

#### 8.4 漏洞检查

| 检查项 | 说明 |
|--------|------|
| 是否有已知漏洞 | 通过 `npm audit` 或 Snyk 检查 |
| 漏洞严重级别 | 高危和严重级别漏洞必须修复后再使用 |
| 依赖链中是否有漏洞 | 间接依赖的漏洞也需要关注 |
| 修复版本是否可用 | 漏洞是否已在更新版本中修复 |

---

### 第九章：重构检查

重构是在保持功能不变的前提下改善代码结构。重构不当会引入回归缺陷，因此每一步都需要严格验证。

#### 9.1 方案审查

| 检查项 | 说明 |
|--------|------|
| 重构原因是否明确 | 用具体的问题描述，而非"代码不够好" |
| 重构目标是否清晰 | 重构后应该变成什么样，有明确的验收标准 |
| 影响范围是否评估 | 列出所有需要改动的文件和模块 |
| 实施步骤是否有计划 | 分几步做，每步做什么，有明确的顺序 |
| 回滚方案是否准备 | 如果重构出了问题，如何快速恢复到重构前的状态 |

#### 9.2 测试验证

| 检查项 | 说明 |
|--------|------|
| 重构前是否有基线测试 | 手动或自动地记录当前功能的正确状态 |
| 核心功能是否逐一验证 | 重构后跑一遍核心流程 |
| 边界条件是否覆盖 | 不只是正常流程，边界场景也要验证 |
| 是否有回归测试 | 确保重构没有影响其他不相关的功能 |

#### 9.3 验证检查

| 检查项 | 说明 |
|--------|------|
| 外部行为是否不变 | 用户看到的界面、操作流程与重构前完全一致 |
| API 接口是否不变 | 请求和响应的结构没有变化 |
| 数据格式是否不变 | 存储和读取的数据结构没有变化 |
| 性能是否有退化 | 重构后的运行速度没有明显下降 |

#### 9.4 分离检查

| 检查项 | 说明 |
|--------|------|
| 重构和功能开发是否分开提交 | 同一个提交中不做重构又做新功能 |
| 重构提交是否可独立回滚 | 重构提交可以单独 revert，不影响功能提交 |
| 是否有"顺手"改了不相关的地方 | 重构只改需要改的，不改不相关的 |

---

### 第十章：架构健康检查

架构健康检查是对项目整体结构的定期体检。不像其他维度聚焦于具体变更，架构检查从全局视角审视项目是否在健康地成长。

#### 10.1 DRY 检查

| 检查项 | 说明 |
|--------|------|
| 是否有重复的业务逻辑 | 同一业务规则在多个地方实现 |
| 是否有重复的工具函数 | 功能相同的函数散落在不同模块 |
| 是否有重复的组件 | 外观和功能相似的组件可以合并 |
| 是否有重复的类型定义 | 同一实体的类型在多处定义 |

**判断标准**：同一段代码（或逻辑等价的代码）出现 3 次以上，应该提取为公共函数/组件/模块。出现 2 次时观察——如果未来可能继续增加，也应提前提取。

#### 10.2 一致性检查

| 检查项 | 说明 |
|--------|------|
| 命名风格是否统一 | 同一概念在整个项目中使用相同的名字 |
| 代码组织是否统一 | 同类模块的内部结构是否一致 |
| 错误处理是否统一 | 全局使用相同的错误处理模式 |
| API 风格是否统一 | 所有 API 遵循相同的风格约定 |
| 样式方案是否统一 | 不混用多种 CSS 方案 |

#### 10.3 解耦检查

| 检查项 | 说明 |
|--------|------|
| 模块之间是否通过接口交互 | 不直接访问其他模块的内部实现 |
| 是否有循环依赖 | A 依赖 B，B 又依赖 A |
| 数据层和业务层是否分离 | 组件不直接操作数据库 |
| 配置和实现是否分离 | 环境相关的值不在代码中硬编码 |

#### 10.4 结构检查

| 检查项 | 说明 |
|--------|------|
| 目录结构是否清晰 | 新加入的开发者能快速找到代码 |
| 文件命名是否有规律 | 看文件名就能大致知道文件内容 |
| 入口文件是否简洁 | 模块的 index.ts 只做导出，不写业务逻辑 |
| 是否有"上帝文件" | 单个文件承担了过多职责 |

#### 10.5 可扩展性检查

| 检查项 | 说明 |
|--------|------|
| 新增功能模块是否方便 | 现有架构能否容纳新模块而不大改 |
| 新增字段是否方便 | 数据模型能否容纳新字段而不影响旧逻辑 |
| 新增 API 是否方便 | 接口层能否容纳新端点而不破坏现有约定 |
| 配置是否灵活 | 不同环境的差异通过配置切换而非改代码 |

#### 10.6 可读性检查

| 检查项 | 说明 |
|--------|------|
| 代码是否能自解释 | 不看注释就能理解代码意图 |
| 函数长度是否合理 | 单个函数不超过 50 行为佳 |
| 嵌套深度是否合理 | 嵌套不超过 3 层 |
| 注释是否必要且准确 | 注释解释"为什么"而非重复"做了什么" |

---

### 第十一章：项目可恢复性

项目可恢复性关注的是：如果发生意外（硬盘损坏、代码误删、服务器宕机），项目能否快速恢复。这是整个质量体系的兜底保障。

#### 11.1 README 检查

| 检查项 | 说明 |
|--------|------|
| 项目是否有 README | 包含项目简介、技术栈、启动方式 |
| 启动步骤是否可复现 | 新人按照 README 能独立启动项目 |
| 环境要求是否列出 | Node 版本、依赖工具版本、系统要求 |
| 重要配置是否说明 | 环境变量的含义和获取方式 |

#### 11.2 环境可恢复性

| 检查项 | 说明 |
|--------|------|
| 依赖安装是否可重现 | lock 文件提交到版本控制，安装后环境一致 |
| 开发环境是否可快速搭建 | 从零开始到项目运行不超过 3 步 |
| 数据库是否有初始数据 | 初始数据或种子脚本是否可自动执行 |
| 环境变量是否文档化 | 每个环境变量的用途和获取方式都有说明 |

#### 11.3 部署可恢复性

| 检查项 | 说明 |
|--------|------|
| 部署步骤是否文档化 | 从代码到上线的完整步骤 |
| 回滚方案是否明确 | 上线出问题时如何快速回退 |
| 数据库回滚是否可行 | 数据库变更是否有回滚脚本 |
| 监控和告警是否配置 | 关键指标异常时能及时通知 |

#### 11.4 数据导出与备份

| 检查项 | 说明 |
|--------|------|
| 关键数据是否有导出功能 | 用户数据、业务数据能导出为通用格式 |
| 备份策略是否明确 | 备份频率、保留时间、恢复流程 |
| 备份是否定期验证 | 备份文件能否正常恢复（定期测试） |

#### 11.5 决策记录

| 检查项 | 说明 |
|--------|------|
| 重大技术决策是否记录 | 为什么选了这个技术栈、这个架构方案 |
| 决策的替代方案是否记录 | 考虑过哪些替代方案，为什么没选 |
| 已知的技术债是否记录 | 已知的不完美之处和计划修复的时间 |
| 变更日志是否维护 | 每个版本的变更是否记录在 CHANGELOG 中 |

## 第三篇：使用指南

### 第十二章：如何使用本清单

#### 12.1 不同阶段的检查重点

不同项目阶段关注的维度不同，不必每次都做全量检查。

**项目初期**（从零到第一个可用版本）：

| 重点维度 | 原因 |
|----------|------|
| 架构健康检查 | 初始架构决定了后续所有开发的效率 |
| 数据库扩展检查 | 初始数据模型设计影响面最大 |
| 项目可恢复性 | 基础设施（README、环境、备份）从第一天就要有 |

**开发中**（日常迭代）：

| 重点维度 | 原因 |
|----------|------|
| AI 交付检查 | 每次 AI 产出代码后的第一道关卡 |
| 代码审查 | 每次合并前的质量关卡 |
| 功能验收 | 每个功能完成时的正确性验证 |
| 依赖引入检查 | 每次引入新依赖时的评估 |

**上线前**（发布前的集中检查）：

| 重点维度 | 原因 |
|----------|------|
| 功能验收 | 全量功能走查 |
| 体验验收 | 用户视角的完整体验检查 |
| 安全检查 | 上线前的安全审计 |
| 数据库扩展检查 | 确保数据库变更经过验证 |
| 项目可恢复性 | 确保部署和回滚方案就绪 |

**运维期**（上线后的持续维护）：

| 重点维度 | 原因 |
|----------|------|
| 架构健康检查 | 定期（每月）审视架构是否在退化 |
| 安全检查 | 定期安全审计和依赖漏洞扫描 |
| 项目可恢复性 | 定期验证备份和恢复流程 |
| 重构检查 | 渐进式改善技术债 |
