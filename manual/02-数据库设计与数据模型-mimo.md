# 数据库设计与数据模型

- **日期**：2026-08-21
- **版本**：v1.0
- **适用范围**：适用于个人开发者与 AI 协作的中小型项目，以 Web 应用为主要场景。本文使用通用场景示例（博客平台、电商后台、团队协作工具等），不绑定特定技术栈或项目。

## 第一篇：设计方法论

数据库设计是项目的地基。地基打得牢，上层建筑才稳；地基打歪了，后续所有的开发、维护、扩展都会受影响。本篇从实体识别开始，逐步建立完整的数据库设计方法论。

### 第一章：实体识别与关系分析

#### 1.1 从需求中识别实体

设计数据库的第一步，是从用户需求中提取实体和关系。一个实用的方法是"名词→实体，动词→关系"的映射。

**提取步骤**：

1. 阅读需求文档，列出所有名词
2. 筛选出需要持久化存储的名词（排除纯界面概念、临时状态）
3. 为每个实体确定核心属性
4. 分析实体之间的关系（通过动词连接）

> **示例——博客平台场景**：需求描述为"用户可以发布文章，文章下可以有评论，评论可以被回复，文章可以有多个标签"。
>
> - 名词提取：用户、文章、评论、标签
> - 需要存储的实体：`User`、`Article`、`Comment`、`Tag`
> - 动词提取：发布（User → Article）、评论（Article → Comment）、被回复（Comment → Comment）、拥有（Article ↔ Tag）
> - 关系判断：一个用户可以发布多篇文章（一对多），一篇文章可以有多个评论（一对多），一篇文章可以有多个标签（多对多），评论可以回复评论（自引用一对多）

**筛选标准——这个名词要不要建表？**

| 判断条件 | 说明 | 示例 |
|----------|------|------|
| 需要持久化存储 | 数据关掉应用后还需要保留 | 用户信息、订单记录 |
| 需要独立查询 | 需要按条件筛选、排序、分页 | 文章列表按时间排序 |
| 有独立的生命周期 | 可以独立创建、修改、删除 | 评论可以独立删除 |
| 包含多个属性 | 不是一个简单的值，而是一组信息 | 地址（省、市、区、详细地址） |

如果一个名词只包含一个简单值，通常作为字段而不是独立的表。例如"文章的阅读量"只是一个数字字段，不需要单独建表。

#### 1.2 实体关系分析

确定了实体之后，需要判断实体之间的关系类型。三种基本关系如下：

| 关系类型 | 含义 | 数据库实现 | 示例 |
|----------|------|------------|------|
| 一对一（1:1） | A 的一条记录只对应 B 的一条记录 | 任意一方的表加外键，或合并为一张表 | 用户 ↔ 用户资料（一个用户只有一份资料） |
| 一对多（1:N） | A 的一条记录对应 B 的多条记录 | "多"方的表加外键指向"一"方 | 用户 → 文章（一个用户有多篇文章） |
| 多对多（M:N） | A 的一条记录对应 B 的多条记录，反之亦然 | 创建中间关联表 | 文章 ↔ 标签（一篇文章有多个标签，一个标签下有多篇文章） |

**判断方法**：对两个实体分别提问——

- "一个 A 能对应几个 B？"
- "一个 B 能对应几个 A？"

两个答案组合起来就确定了关系类型。

> **示例——电商后台场景**：分析"商品"和"分类"的关系。一个商品属于一个分类（假设不做多分类），一个分类下有多个商品。答案是：1 个 A → N 个 B，1 个 B → 1 个 A。结论是一对多关系，在商品表中加 `category_id` 外键。

**自引用关系**：当一个实体和自身存在关系时，称为自引用。例如评论的回复——一条评论的父评论还是评论本身。在表中加一个 `parent_id` 字段指向自身的 `id`。

#### 1.3 实体关系图示例

以下是一个博客平台的实体关系图：

```
┌──────────────┐       ┌──────────────────┐       ┌──────────────┐
│     User     │       │     Article      │       │     Tag      │
├──────────────┤       ├──────────────────┤       ├──────────────┤
│ id (PK)      │──┐    │ id (PK)          │    ┌──│ id (PK)      │
│ username     │  │    │ title            │    │  │ name         │
│ email        │  │    │ content          │    │  │ slug         │
│ password_hash│  │    │ author_id (FK)───│────┘  └──────────────┘
│ avatar_url   │  └───▶│ status           │
│ created_at   │       │ published_at     │       ┌──────────────────┐
│ updated_at   │       │ created_at       │       │  Article_Tag     │
│ deleted_at   │       │ updated_at       │       ├──────────────────┤
└──────────────┘       │ deleted_at       │       │ article_id (FK)──│──▶ Article.id
                       └───────┬──────────┘       │ tag_id (FK)─────│──▶ Tag.id
                               │                  └──────────────────┘
                               │
                               │ 1:N
                               ▼
                       ┌──────────────────┐
                       │     Comment      │
                       ├──────────────────┤
                       │ id (PK)          │
                       │ article_id (FK)──│──▶ Article.id
                       │ author_id (FK)───│──▶ User.id
                       │ parent_id (FK)───│──▶ Comment.id (自引用)
                       │ content          │
                       │ created_at       │
                       │ updated_at       │
                       │ deleted_at       │
                       └──────────────────┘
```

**关系总结**：

- User → Article：一对多（一个用户发布多篇文章）
- Article ↔ Tag：多对多（通过 Article_Tag 中间表）
- Article → Comment：一对多（一篇文章有多条评论）
- Comment → Comment：自引用一对多（评论可以回复评论）
- User → Comment：一对多（一个用户可以发多条评论）

### 第二章：字段设计

实体关系确定后，接下来设计每个实体的具体字段。字段设计决定了数据的存储方式、查询效率和扩展能力。

#### 2.1 主键设计

主键是每条记录的唯一标识。两种常见方案的对比：

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 自增 ID（INTEGER AUTO_INCREMENT） | 简单、紧凑、查询高效、索引友好 | 暴露数据量（ID=1000 说明有约 1000 条记录），分布式环境下可能冲突 | 内部系统、单数据库、不需要暴露给外部 |
| UUID | 全局唯一、不暴露数据量、分布式安全 | 占用空间大（36 字符 vs 4 字节整数）、索引效率略低、不可读 | 需要对外暴露 ID、分布式系统、多端同步 |

**推荐策略**：

- 内部系统优先使用自增 ID，简单高效
- 如果需要对外暴露（如 API 返回给前端），可以自增 ID 作内部主键，另加一个 `uuid` 字段作为对外标识
- 使用 UUID 时推荐 UUIDv7（时间有序），兼顾唯一性和索引性能

#### 2.2 时间字段

每张表都应包含以下标准时间字段：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `created_at` | TIMESTAMP / DATETIME | 记录创建时间，插入时自动设置 |
| `updated_at` | TIMESTAMP / DATETIME | 记录最后修改时间，每次更新时自动刷新 |

**设置方式**（以 MySQL 为例）：

```sql
CREATE TABLE articles (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

**设计原则**：时间字段一旦设置就不应被业务代码手动修改，由数据库自动管理。

#### 2.3 软删除

软删除是指不真正删除数据，而是标记为"已删除"状态。推荐所有表都支持软删除。

**为什么推荐软删除**：

| 原因 | 说明 |
|------|------|
| 数据安全 | 误删数据可以恢复，不需要从备份还原 |
| 审计需求 | 保留操作历史，满足合规要求 |
| 关联数据 | 硬删除可能破坏外键约束或导致关联数据孤立 |
| 分析统计 | 保留历史数据用于分析（如"本月删除了多少篇文章"） |

**实现方式**：在表中添加 `deleted_at` 字段。

```sql
-- 添加软删除字段
ALTER TABLE articles ADD COLUMN deleted_at TIMESTAMP NULL DEFAULT NULL;

-- 软删除操作（不是 DELETE，而是 UPDATE）
UPDATE articles SET deleted_at = NOW() WHERE id = 123;

-- 查询时排除已删除记录
SELECT * FROM articles WHERE deleted_at IS NULL;

-- 恢复已删除记录
UPDATE articles SET deleted_at = NULL WHERE id = 123;
```

**注意事项**：

- 查询时必须始终加上 `WHERE deleted_at IS NULL` 条件（或通过数据库视图/ORM 自动过滤）
- 软删除后，唯一约束（如唯一索引）可能需要处理——常见方案是将唯一索引改为包含 `deleted_at` 的复合索引
- 定期清理超过保留期的软删除数据（如保留 90 天）

#### 2.4 字段类型选择

常见字段类型的选择指南：

| 数据 | 推荐类型 | 避免使用 | 原因 |
|------|----------|----------|------|
| 主键 ID | BIGINT / INT | VARCHAR | 整型索引效率更高 |
| 短文本（标题、名称） | VARCHAR(255) | TEXT | VARCHAR 可以建索引，TEXT 不行 |
| 长文本（正文、描述） | TEXT / MEDIUMTEXT | VARCHAR(10000) | 超长 VARCHAR 无意义 |
| 布尔值 | TINYINT(1) 或 BOOLEAN | ENUM('true','false') | TINYINT 存储更高效 |
| 金额/价格 | DECIMAL(10,2) 或整数（分） | FLOAT / DOUBLE | 浮点数有精度问题 |
| 日期时间 | TIMESTAMP / DATETIME | VARCHAR / INT 存时间戳 | 原生时间类型支持时间函数 |
| JSON 数据 | JSON（MySQL 5.7+） | TEXT 手动序列化 | 原生 JSON 支持索引和查询 |
| 状态/枚举 | VARCHAR 或 TINYINT | ENUM | ENUM 修改列值需要 ALTER TABLE |
| 邮箱 | VARCHAR(320) | CHAR(255) | RFC 规定邮箱最长 320 字符 |
| URL | VARCHAR(2048) | TEXT | URL 有长度限制，VARCHAR 可索引 |

**金额处理的两种方案**：

| 方案 | 做法 | 适用场景 |
|------|------|----------|
| 整数存储（分） | 价格 19.99 元存储为 1999 | 计算精度要求高，如电商支付 |
| DECIMAL 存储 | DECIMAL(10,2) 直接存 19.99 | 展示为主，计算简单 |

#### 2.5 字段命名规范

**表名规范**：

| 规则 | 示例 |
|------|------|
| 使用复数形式 | `users`、`articles`、`order_items` |
| 使用 snake_case | `order_items`（不是 `orderItems`） |
| 中间关联表：两端表名用下划线连接 | `article_tags`（不是 `article_tag`） |
| 避免使用保留字 | 不用 `order`（SQL 保留字），用 `orders` |

**字段名规范**：

| 规则 | 示例 |
|------|------|
| 使用 snake_case | `created_at`（不是 `createdAt`） |
| 外键命名：关联表名（单数）+ `_id` | `author_id`、`category_id` |
| 布尔字段用 `is_`/`has_` 前缀 | `is_published`、`has_avatar` |
| 时间字段统一后缀 `_at` | `created_at`、`deleted_at` |
| 避免缩写 | `description`（不是 `desc`，因为 `DESC` 是 SQL 关键字） |

### 第三章：索引设计

索引是提升查询性能的关键手段，但索引不是越多越好。需要在查询性能和写入性能之间找到平衡。

#### 3.1 何时需要索引

以下场景应该建立索引：

| 场景 | 原因 | 示例 |
|------|------|------|
| WHERE 条件频繁使用的字段 | 加速筛选 | `WHERE status = 'published'` |
| ORDER BY 排序字段 | 避免排序操作 | `ORDER BY created_at DESC` |
| JOIN 关联字段 | 加速表连接 | `article.author_id = user.id` |
| 外键字段 | 加速关联查询和级联操作 | 所有 `_id` 字段 |
| 高选择性字段 | 值分布广，区分度高 | `email`、`uuid` |
| 唯一约束字段 | 数据完整性 | `username`、`email` |

**判断选择性**：选择性 = 不同值的数量 / 总行数。选择性越高（接近 1），索引效果越好。例如 `email` 字段几乎每行都不同，选择性很高；而 `status` 字段只有几个枚举值，选择性很低。

#### 3.2 何时不需要索引

过度索引的危害和不需要索引的场景：

| 场景 | 原因 |
|------|------|
| 小表（几百行以下） | 全表扫描比索引查找更快 |
| 频繁写入、很少查询的表 | 索引会拖慢 INSERT/UPDATE/DELETE |
| 低选择性字段（如 `gender`） | 索引区分度太低，优化器不会使用 |
| 频繁变更的字段 | 索引需要频繁重建 |
| 只有少量不同值的字段 | 不如直接全表扫描 |

**过度索引的危害**：

- 每次 INSERT/UPDATE/DELETE 都需要同步更新所有索引，写入性能下降
- 占用额外的磁盘空间
- 增加数据库维护成本（索引碎片整理等）

#### 3.3 复合索引

当查询条件涉及多个字段时，使用复合索引（联合索引）。

**设计原则**：

1. **最左前缀原则**：复合索引 `(A, B, C)` 可以加速 `WHERE A = ?`、`WHERE A = ? AND B = ?`、`WHERE A = ? AND B = ? AND C = ?` 的查询，但不能加速 `WHERE B = ?` 或 `WHERE C = ?` 的查询
2. **高选择性字段放前面**：选择性高的字段放索引前面，能更快缩小范围
3. **等值条件在前，范围条件在后**：如果一个字段是等值查询（`= ?`），另一个是范围查询（`> ?`、`BETWEEN`），等值字段放前面

> **示例——电商后台场景**：订单列表页面需要按"状态 + 时间"筛选。查询是 `WHERE status = 'shipped' ORDER BY created_at DESC`。复合索引应建为 `(status, created_at)`——`status` 是等值条件放前面，`created_at` 是排序字段放后面。

**常见错误**：为每个查询条件单独建索引，而不是建立复合索引。数据库一次查询通常只能使用一个索引，多个单字段索引的效率远不如一个设计合理的复合索引。

## 第二篇：扩展方法

项目上线后，数据库结构几乎不可避免地需要调整。本篇讨论如何安全地扩展已有数据模型，避免因变更导致数据丢失或服务中断。

### 第四章：安全扩展已有数据模型

#### 4.1 四种扩展场景

数据库扩展可以归纳为四种场景：

| 扩展类型 | 说明 | 风险等级 | 示例 |
|----------|------|----------|------|
| 新增字段 | 给已有表添加新列 | 低 | 给用户表添加 `phone_number` 字段 |
| 新增表 | 创建全新的表 | 低 | 新增"通知"表 |
| 修改字段类型 | 改变已有字段的数据类型或约束 | 中 | 将 `price` 从 INT 改为 DECIMAL |
| 拆分与合并 | 将一张表拆为多张，或将多张合并 | 高 | 将用户表中的地址信息拆到独立的地址表 |

#### 4.2 新增字段

新增字段是风险最低的扩展操作，但仍需遵循规范。

**安全步骤**：

1. 确认新字段的类型、默认值、是否允许 NULL
2. 编写迁移脚本（包含 up 和 down）
3. 在测试环境验证
4. 执行迁移
5. 更新应用代码读写新字段

**注意事项**：

| 要点 | 说明 |
|------|------|
| 新字段允许 NULL 或设置默认值 | 避免影响已有数据的读取 |
| 大表加字段要谨慎 | MySQL 5.6+ 的 Online DDL 支持大部分场景，但大表仍可能锁表 |
| 先加字段，再加索引 | 分两步操作，降低风险 |
| 记录迁移日志 | 方便后续回滚 |

**示例**：

```sql
-- UP: 新增字段
ALTER TABLE users ADD COLUMN phone_number VARCHAR(20) NULL;

-- DOWN: 回滚（删除字段）
ALTER TABLE users DROP COLUMN phone_number;
```

#### 4.3 新增表

新增表是最安全的扩展操作，不会影响已有数据。

**安全步骤**：

1. 设计表结构（字段、类型、约束、索引）
2. 确认与已有表的关联关系
3. 编写建表脚本
4. 在测试环境验证
5. 执行建表

**注意事项**：

- 建表时就包含软删除字段和时间字段
- 建表时就建立必要的索引
- 外键约束根据项目实际情况决定是否启用（ORM 项目通常不启用数据库层面的外键）

#### 4.4 修改字段类型

修改字段类型是风险中等的操作，需要特别谨慎。

**风险点**：

| 风险 | 说明 |
|------|------|
| 数据丢失 | 类型收窄可能导致数据被截断（如 VARCHAR(50) → VARCHAR(20)） |
| 锁表 | 某些类型变更需要重建表，期间会锁表 |
| 应用兼容 | 修改类型后，所有读写该字段的代码都需要同步修改 |
| 索引失效 | 类型变更可能导致已有索引失效 |

**安全流程**：

```
修改字段类型流程：

1. 评估影响
   ├── 这个字段有多少数据？
   ├── 修改后是否影响已有数据？
   ├── 所有使用这个字段的代码在哪里？
   └── 修改期间能否接受短暂停服？
         │
         ▼
2. 编写迁移脚本（含回滚方案）
         │
         ▼
3. 在测试环境验证
   ├── 数据完整性验证
   ├── 应用功能验证
   └── 性能验证
         │
         ▼
4. 备份数据
         │
         ▼
5. 低峰期执行迁移
         │
         ▼
6. 验证线上数据和功能
         │
         ▼
7. 观察期（1-3 天）
```

**示例**：

```sql
-- UP: 将 price 从 INT 改为 DECIMAL（存储分为元）
-- 注意：如果有旧数据需要迁移
ALTER TABLE products MODIFY COLUMN price DECIMAL(10,2) NOT NULL DEFAULT 0;

-- DOWN: 回滚（注意数据可能已经变化）
ALTER TABLE products MODIFY COLUMN price INT NOT NULL DEFAULT 0;
```

#### 4.5 拆分与合并

拆分与合并是最复杂的数据库扩展操作，风险最高。

**何时需要拆分**：

| 信号 | 说明 |
|------|------|
| 单表数据量超过 500 万行 | 查询性能显著下降 |
| 一张表承担多种职责 | 如用户表同时存了个人资料、登录信息、偏好设置 |
| 字段之间关联性弱 | 不同字段组的更新频率差异很大 |

**拆分的安全流程**：

```
表拆分流程：

1. 分析依赖
   ├── 哪些代码在读写要拆分的字段？
   ├── 是否有外键关联？
   └── 是否有索引依赖？
         │
         ▼
2. 创建新表
   ├── 新表包含拆出的字段
   ├── 新表包含必要的索引
   └── 新表包含关联字段（外键）
         │
         ▼
3. 数据迁移
   ├── 将旧表数据复制到新表
   ├── 验证数据一致性
   └── 这一步可以重复执行（幂等）
         │
         ▼
4. 修改应用代码
   ├── 读写操作改为指向新表
   └── 分步切换，先读旧表+写新表，再完全切换
         │
         ▼
5. 验证运行
   ├── 功能验证
   ├── 性能验证
   └── 观察期
         │
         ▼
6. 清理旧字段（可选）
   ├── 确认无代码引用旧字段后删除
   └── 或保留作为历史数据
```

**合并操作**通常比拆分更危险，因为涉及数据去重和冲突处理。建议尽量避免合并操作，如果必须合并，按照"先复制→再验证→再切换"的三步走策略。

#### 4.6 数据库扩展流程图

以下是完整的数据库扩展决策流程：

```
需要修改数据库结构
        │
        ▼
   ┌────────────┐
   │ 变更类型？  │
   └─────┬──────┘
         │
    ┌────┴────┬──────────┬────────────┐
    ▼         ▼          ▼            ▼
 新增字段   新增表    修改类型    拆分/合并
    │         │          │            │
    ▼         ▼          ▼            ▼
 风险低     风险低    风险中       风险高
    │         │          │            │
    ▼         ▼          ▼            ▼
 编写迁移   编写建表   评估影响    详细方案
 脚本       脚本       +备份       +数据迁移
    │         │          │            │
    └────┬────┴────┬─────┴─────┬──────┘
         ▼         ▼           ▼
      测试环境验证
         │
         ▼
      低峰期执行
         │
         ▼

         │
         ▼

```

## 第三篇：变更管理

数据库变更不同于代码变更——代码出了 bug 可以 hotfix，数据库出了问题可能导致数据丢失。因此数据库变更需要更严格的管理流程。

### 第五章：Schema 迁移

#### 5.1 迁移脚本规范

每次数据库结构变更都应该通过迁移脚本执行，而不是手动操作数据库。

**迁移脚本的基本结构**：

```
migrations/
├── 001_create_users.sql
├── 002_create_articles.sql
├── 003_add_email_index.sql
├── 004_create_comments.sql
└── ...
```

**每个迁移脚本必须包含 up 和 down 两个部分**：

```sql
-- ============================================
-- 迁移：003_add_email_index
-- 说明：为 users 表的 email 字段添加唯一索引
-- 日期：2026-08-21
-- ============================================

-- UP: 执行迁移
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- DOWN: 回滚迁移
DROP INDEX idx_users_email ON users;
```

**命名规范**：

| 规则 | 示例 |
|------|------|
| 三位数字前缀 + 下划线 + 动作描述 | `003_add_email_index.sql` |
| 动作用 snake_case | `create_users_table.sql`、`add_phone_to_users.sql` |
| 包含迁移说明注释 | 文件头部注释说明本次迁移的目的 |

**禁止事项**：

- 禁止手动在生产数据库执行 SQL 变更
- 禁止跳过迁移编号
- 禁止修改已执行的迁移文件（应该新建一个迁移来修正）
- 禁止在迁移脚本中包含业务数据（迁移只处理结构变更）

#### 5.2 版本管理

Schema 版本需要与应用版本对应，确保数据库结构和应用代码同步。

**版本对应关系**：

```
应用版本 v1.0.0 → Schema 版本 001-005（初始数据库结构）
应用版本 v1.1.0 → Schema 版本 006-008（新增通知功能）
应用版本 v1.2.0 → Schema 版本 009（修改订单表结构）
```

**版本记录方式**：

在数据库中维护一张 `schema_migrations` 表，记录已执行的迁移：

```sql
CREATE TABLE schema_migrations (
    version VARCHAR(255) PRIMARY KEY,
    executed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

每次执行迁移后记录版本号，下次启动时检查是否有未执行的迁移。

#### 5.3 回滚方案

每个迁移的 down 部分就是回滚方案。设计可回滚迁移的原则：

| 原则 | 说明 |
|------|------|
| down 操作必须与 up 操作对称 | up 加了字段，down 就删字段 |
| 数据类变更要谨慎 | up 插入的数据，down 可能需要删除（但要确认是否是业务数据） |
| 分步操作 | 复杂变更拆分为多个迁移，每个迁移都可以独立回滚 |
| 保留旧数据 | 删除字段/表之前，先把数据导出到备份表 |

**不能回滚的情况**：

- 删除了字段且 down 中没有数据恢复逻辑
- 数据类型的不可逆变更（如从 VARCHAR 改为 INT，部分数据可能丢失）
- 这类操作需要提前手动备份

#### 5.4 迁移检查清单

每次执行迁移前，逐项检查：

| 检查项 | 说明 |
|--------|------|
| 迁移脚本是否包含 up 和 down | 确保可以回滚 |
| 是否在测试环境验证过 | 包括功能验证和数据验证 |
| 是否备份了数据 | 大表变更前必须备份 |
| 是否在低峰期执行 | 避免影响线上用户 |
| 回滚方案是否明确 | 出问题时能快速恢复 |
| 是否通知了相关人员 | 团队协作时需要通知 |
| 影响范围是否评估清楚 | 涉及哪些表、哪些代码、哪些功能 |
| 是否检查了数据兼容性 | 新结构能否兼容旧数据 |

## 第四篇：AI 协作

在 AI 协作开发中，数据库设计是 AI 最容易出问题的领域之一。AI 擅长生成代码，但数据库设计需要全局思维和业务理解。本篇给出与 AI 协作时的数据库规范。

### 第六章：AI 数据库协作规范

#### 6.1 AI 数据库设计验证维度

AI 生成的数据库设计需要从四个维度验证：

**维度一：结构完整性**

| 检查项 | 说明 |
|--------|------|
| 是否所有实体都已建表 | 需求中的每个实体都有对应的表 |
| 字段类型是否合理 | 不用 FLOAT 存金额，不用 VARCHAR 存大量数据 |
| 主键和外键是否完整 | 每张表都有主键，关联关系通过外键体现 |
| 是否包含标准字段 | created_at、updated_at、deleted_at |
| 命名是否统一 | 所有表名、字段名遵循命名规范 |

**维度二：扩展性**

| 检查项 | 说明 |
|--------|------|
| 是否预留了扩展字段 | 常见场景预留 JSON 类型的扩展字段 |
| 表结构是否支持未来需求 | 不需要大幅重构就能支持新功能 |
| 是否避免了过度设计 | 不需要的功能不建表、不加字段 |

**维度三：可维护性**

| 检查项 | 说明 |
|--------|------|
| 迁移脚本是否完整 | 每个结构变更都有对应的迁移文件 |
| 是否有回滚方案 | 每个迁移都有 down 操作 |
| 是否有数据模型文档 | 数据结构有文档记录 |

**维度四：兼容性**

| 检查项 | 说明 |
|--------|------|
| 与已有表结构是否兼容 | 新表与已有表的关系是否正确 |
| 与应用代码是否匹配 | 数据库结构和 ORM 模型是否一致 |
| 是否考虑了多端同步 | 如果有离线场景，是否支持数据同步 |

#### 6.2 AI 常见数据库错误

| 错误类型 | 具体表现 | 防范方法 |
|----------|----------|----------|
| 忘记时间字段 | 表中没有 created_at/updated_at | 建表模板中固定包含时间字段 |
| 忘记软删除 | 硬删除数据，无法恢复 | 所有表默认加 deleted_at |
| 金额用浮点数 | 用 FLOAT/DOUBLE 存价格，产生精度问题 | 强制要求金额用 DECIMAL 或整数 |
| 过度使用 TEXT | 所有文本字段都用 TEXT | 明确字段用途，短文本用 VARCHAR |
| 缺少索引 | 查询字段没有索引，性能差 | 在设计阶段就确认索引策略 |
| 命名不一致 | 有的表用 camelCase，有的用 snake_case | 建立命名规范并强制执行 |
| 忘记外键关联 | 关联关系不明确，JOIN 查询困难 | 实体关系图中标注所有关联关系 |
| 设计过度 | 为不需要的功能建表、加字段 | 遵循渐进式复杂度原则 |
| 拆分不合理 | 一个实体被拆成过多的表，查询时需要大量 JOIN | 除非有明确的性能或业务需求，否则不拆 |
| 缺少迁移脚本 | 直接在数据库上执行 SQL | 所有变更通过迁移脚本 |

#### 6.3 数据库变更的确认机制

以下操作必须获得用户确认后才能执行：

| 操作类型 | 说明 | 确认方式 |
|----------|------|----------|
| 删除表或字段 | 涉及数据丢失风险 | 明确告知影响范围，用户确认 |
| 修改字段类型 | 可能影响已有数据 | 说明变更原因和风险，用户确认 |
| 拆分或合并表 | 高风险操作 | 提供详细方案，用户确认后执行 |
| 添加外键约束 | 可能影响写入性能 | 说明原因，用户确认 |
| 修改索引策略 | 影响查询性能 | 说明影响范围，用户确认 |
| 大表结构变更 | 可能锁表影响服务 | 说明执行时间和影响，用户确认 |

以下操作可以直接执行，无需确认：

| 操作类型 | 说明 |
|----------|------|
| 新增表 | 不影响已有数据 |
| 新增可空字段 | 不影响已有数据 |
| 新增索引 | 不影响数据，只影响性能 |
| 新增默认值 | 不影响已有数据读取 |
