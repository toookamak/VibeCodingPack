# 开发里程碑计划

- **日期**：2026-08-21
- **版本**：v1.0
- **适用范围**：适用于个人开发者与 AI 协作的中小型项目，以 Web 应用为主要场景，但方法论不限于特定技术栈。本文使用通用场景示例，不绑定特定项目。

---

## 第一篇：方法论

在讨论具体执行之前，先建立里程碑设计的方法论。方法论决定了里程碑拆得对不对、排得合不合理。方法论不对，后面的执行全是返工。

### 第一章：里程碑设计原则

#### 1.1 核心原则

设计里程碑时遵循四条核心原则：

**可运行成果**

每个里程碑的交付物必须是可运行的，而不是一堆"做了一半"的代码。用户或开发者在里程碑结束时，应该能看到一个能跑的东西——哪怕功能很简陋。

> **示例——博客平台场景**：里程碑 1 的交付物是"能创建文章、能查看文章列表"，而不是"数据库表设计完成 + API 接口定义完成"。后者虽然也是进展，但无法运行、无法验证。

**按场景排列，而非按技术层排列**

里程碑应该按照用户使用的场景来组织，而不是按照技术层（先做数据库、再做 API、再做前端）。按场景排列的好处是：每个里程碑结束后都能端到端验证。

| 排列方式 | 示例 | 问题 |
|----------|------|------|
| ❌ 按技术层 | M1: 设计数据库 → M2: 实现 API → M3: 做前端页面 | M1 结束后无法验证任何功能 |
| ✅ 按场景 | M1: 文章创建与查看 → M2: 用户评论 → M3: 文章搜索 | 每个里程碑都能端到端跑通 |

**1～2 周周期**

每个里程碑的开发周期控制在 1～2 周。太短（1～2 天）会导致里程碑碎片化，管理成本高于开发成本；太长（1 个月以上）会导致风险累积——做了一个月才发现方向偏了。

**先跑通再完善**

第一个里程碑用最简陋的方式跑通核心流程，后续里程碑再逐步完善。不要在一个里程碑里同时做"基础功能"和"完美体验"。

#### 1.2 五步拆分法

将项目拆分为里程碑，遵循五步流程：

1. **列功能**——把产品需要的所有功能列出来，不需要排序，先穷举
2. **定核心**——从功能列表中找出核心功能：没有它，产品就不能用的功能
3. **按场景分组**——将功能按用户使用场景分组，每组对应一个里程碑
4. **估工作量**——为每个里程碑估算大致工作量，确保在 1～2 周内可完成
5. **排顺序**——按照依赖关系和业务优先级排列里程碑顺序

> **示例——电商后台场景**：
> 1. 列功能：商品管理、订单管理、用户管理、数据报表、权限控制、消息通知……
> 2. 定核心：商品管理（没有商品就没法卖）、订单管理（没有订单就没法做生意）
> 3. 按场景分组：M1=商品上架与浏览 → M2=下单与支付 → M3=订单管理与发货 → M4=用户与权限
> 4. 估工作量：M1 约 5 天，M2 约 7 天，M3 约 5 天，M4 约 5 天
> 5. 排顺序：M1 → M2 → M3 → M4（M2 依赖 M1 的商品数据，M3 依赖 M2 的订单数据）

#### 1.3 里程碑拆分流程图

```
┌─────────────┐
│  1. 列功能   │  穷举所有功能，不做筛选
│  （发散）    │  产出：功能列表（可能有 20~50 项）
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  2. 定核心   │  标记"没有它产品不能用"的功能
│  （收敛）    │  产出：核心功能列表（通常 5~10 项）
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 3. 按场景   │  将功能按用户使用场景分组
│    分组      │  产出：场景分组（通常 3~6 个里程碑）
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 4. 估工作量  │  评估每个分组的工作量
│  （校验）    │  产出：工作量评估（超 2 周的要拆分）
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 5. 排顺序    │  按依赖关系和优先级排列
│  （决策）    │  产出：里程碑排序和依赖关系图
└─────────────┘
```

#### 1.4 里程碑拆分的常见错误

| 错误 | 表现 | 正确做法 |
|------|------|----------|
| 粒度太粗 | 一个里程碑包含"整个后台管理系统" | 按场景拆分为多个里程碑 |
| 粒度太细 | 一个里程碑只做"登录页面的样式" | 合并相关功能为一个完整的场景 |
| 按技术层拆分 | M1 只做数据库，M2 只做 API | 按场景拆分，每个里程碑端到端 |
| 没有可运行成果 | 里程碑结束时只有一堆接口定义 | 确保每个里程碑有可运行的交付物 |
| 忽略依赖 | 后面的里程碑依赖前面还没做的功能 | 先画依赖关系图，按拓扑序排列 |

## 第二篇：执行

方法论确定后，进入具体执行。本篇讨论开发循环的具体步骤、里程碑模板、依赖管理和动态调整。

### 第二章：开发循环

#### 2.1 六步开发循环

每个里程碑的开发过程遵循六步循环：

**第一步：需求确认**

明确这个里程碑要做什么。不要模糊地说"做订单功能"，要具体到"支持创建订单、查看订单列表、按状态筛选"。

输出物：里程碑需求清单（功能点列表 + 验收标准）。

**第二步：方案设计**

针对需求清单，设计实现方案。包括：模块划分、数据模型、接口设计、关键组件的结构。

输出物：方案文档（可以是简短的文字描述，不一定需要正式文档）。

**第三步：方案审核**

审核方案的合理性。重点检查：

- 是否符合项目的架构规范（四层架构、关注点分离）
- 是否有过度设计（不需要的抽象、不需要的功能）
- 工作量评估是否合理
- 是否遗漏了边界情况

**第四步：分批实现**

按照方案分批实现，每批只做一个小功能点。每批实现后立即验证：

- 功能是否正常
- 是否引入了新的 bug
- 代码是否符合规范

**第五步：验收测试**

里程碑所有功能点完成后，走一遍完整的用户流程进行验收。

**第六步：文档更新**

更新相关文档：项目上下文文件、变更日志、数据模型文档（如有变更）。

#### 2.2 里程碑模板

以下是可直接使用的里程碑规划模板：

```markdown
# 里程碑 [编号]：[名称]

## 目标
[一句话描述这个里程碑要达成什么]

## 功能清单

| 编号 | 功能点 | 验收标准 | 优先级 | 预估工时 |
|------|--------|----------|--------|----------|
| F1   | [功能描述] | [如何验证完成] | P0/P1/P2 | [小时] |
| F2   | [功能描述] | [如何验证完成] | P0/P1/P2 | [小时] |
| F3   | [功能描述] | [如何验证完成] | P0/P1/P2 | [小时] |

## 依赖关系
- 依赖里程碑 [编号]：[具体依赖什么]
- 被依赖方：里程碑 [编号] 依赖本里程碑的 [具体产出]

## 技术要点
- 数据模型变更：[有/无，具体说明]
- 新增模块：[模块名和职责]
- 外部依赖：[是否需要引入新的第三方库]

## 风险点
- [可能遇到的风险和应对方案]

## 预计周期
- 开始日期：[日期]
- 结束日期：[日期]
- 总工时：[小时]
```

> **示例——博客平台场景**：
>
> ```markdown
> # 里程碑 1：文章创建与查看
>
> ## 目标
> 用户可以创建文章、在列表中查看所有文章、点击查看详情。
>
> ## 功能清单
>

> | F1   | 文章创建页面 | 填写标题和内容后能提交保存 | P0 | 3h |
> | F2   | 文章列表页 | 能按时间倒序展示所有文章标题 | P0 | 3h |
> | F3   | 文章详情页 | 点击标题能查看完整文章内容 | P0 | 2h |
> | F4   | 基础样式 | 页面有基本的排版和样式 | P1 | 2h |
>
> ## 依赖关系
> - 无前置依赖（第一个里程碑）
> - 被依赖方：里程碑 2（评论功能）依赖本里程碑的文章数据结构
>
> ## 技术要点
> - 数据模型变更：新增 article 实体（id, title, content, created_at）
> - 新增模块：features/articles/
> - 外部依赖：无
>
> ## 风险点
> - 文章内容字段选型：富文本 vs Markdown，第一版用 Markdown 即可
>
> ## 预计周期
> - 开始日期：2026-08-21
> - 结束日期：2026-08-28
> - 总工时：10h
> ```

#### 2.3 里程碑间的依赖管理

里程碑之间可能存在依赖关系。处理依赖的核心原则：**先做被依赖的里程碑**。

**依赖类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| 数据依赖 | 后面的里程碑需要前面里程碑的数据结构 | 订单管理依赖商品管理的数据模型 |
| 功能依赖 | 后面的里程碑需要前面里程碑的功能模块 | 搜索功能依赖文章管理的列表数据 |
| 接口依赖 | 后面的里程碑需要调用前面里程碑的 API | 报表模块需要调用订单和商品的查询接口 |

**依赖关系图**：

在规划多个里程碑时，先画出依赖关系图，再决定排列顺序：

```
M1: 商品管理 ──┐
               ├──→ M3: 订单管理 ──→ M5: 数据报表
M2: 用户管理 ──┘         │
                         └──→ M4: 发货与物流
```

**无环原则**：依赖关系图不能有环。如果出现 A 依赖 B、B 又依赖 A 的情况，说明拆分不合理，需要重新拆分。

**处理隐性依赖**：

有些依赖是隐性的——里程碑本身没有直接的数据依赖，但共享了底层组件或工具函数。处理方式：

- 在里程碑 1 中先实现共享组件的基础版本
- 后续里程碑按需扩展，不重复实现

#### 2.4 里程碑计划的动态调整

计划不是一成不变的。以下情况需要调整计划：

**需要调整的信号**：

| 信号 | 说明 | 调整方式 |
|------|------|----------|
| 工时严重偏差 | 实际工时超过预估的 2 倍 | 拆分里程碑，缩减每个里程碑的范围 |
| 需求变更 | 产品需求发生变化 | 重新评估功能清单，调整里程碑内容 |
| 技术障碍 | 遇到预期外的技术难题 | 评估是否需要调整技术方案或降低要求 |
| 优先级变化 | 某个功能的优先级提高或降低 | 调整里程碑的排列顺序 |

**调整原则**：

1. **小调整随时做**——功能增减、工时修正，直接更新里程碑文档
2. **大调整要慎重**——里程碑拆分变更、顺序调整，需要重新评估整体计划
3. **调整后同步记录**——每次调整都更新里程碑文档，标注调整原因和日期
4. **不追求完美计划**——计划是用来指导工作的，不是用来展示的。80% 准确的计划比永远停留在规划阶段好得多

#### 2.5 开发循环时序图

```
需求方                     开发者                     验收方
  │                          │                          │
  │  ── 1.需求确认 ──→       │                          │
  │    (功能清单+验收标准)     │                          │
  │                          │                          │
  │                          │── 2.方案设计 ──→         │
  │                          │  (模块划分+数据模型)      │
  │                          │                          │
  │  ←── 3.方案审核 ──       │                          │
  │    (检查合理性)           │                          │
  │                          │                          │
  │    ┌─────────────────────┤                          │
  │    │ 4.分批实现           │                          │
  │    │                     │                          │
  │    │  ┌─ 功能点1 ─→ 验证 │                          │
  │    │  ├─ 功能点2 ─→ 验证 │                          │
  │    │  └─ 功能点3 ─→ 验证 │                          │
  │    └─────────────────────┤                          │
  │                          │                          │
  │                          │── 5.验收测试 ──→         │
  │                          │  (完整流程走查)           │
  │                          │                          │
  │                          │  ←── 6.文档更新 ──       │
  │                          │  (变更日志+上下文文件)     │
  │                          │                          │
  │  ←── 里程碑完成 ──       │                          │
```

**循环要点**：

- 第 1 步和第 3 步需要与需求方确认，不能自行决定
- 第 4 步的"分批"是关键——不要一次性写完整个里程碑的代码，而是一个功能点一个功能点地实现
- 第 5 步的验收应该走完整的用户流程，而不是单独测试每个功能点
