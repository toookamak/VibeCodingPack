# 开发规范与工程原则

- **日期**：2026-08-21
- **版本**：v1.0
- **适用范围**：适用于个人开发者与 AI 协作的中小型项目，以 Web 应用为主要场景，但方法论不限于特定技术栈。本文使用通用场景示例，不绑定特定项目。

---

## 第一篇：工程原则

在讨论具体规范之前，先建立共识。这些原则是后续所有规范的基础。当规范之间出现矛盾时，回到原则做判断。

### 第一章：核心工程原则

#### 1.1 可维护性优先于开发速度

写得快但写得乱的代码，后续的修改成本会指数级增长。在 AI 协作场景中尤其明显——AI 可以很快产出大量代码，但如果结构混乱，后续对话中 AI 自己都无法正确理解和修改。

> **类比**：好比装修房子——为了省事把电线和水管走同一条线路，装修时确实快了，但以后修水管时很可能把电线也搞坏。

**实践含义**：

- 宁可多花 10 分钟讨论方案，不要急于动手写代码。
- 宁可多拆一个文件，不要把逻辑堆在一起。
- 宁可多写两行类型定义，不要用 any。

| 做法 | 示例 |
|------|------|
| ✅ 好 | 先讨论"这个功能拆成几个模块"，确认后再动手 |
| ❌ 不好 | 接到需求直接让 AI "做一个 XX 功能"，做完才发现结构有问题 |

#### 1.2 单一职责

每个模块、每个文件、每个函数只负责一件事。

**判断方法**：用一句话描述这个模块/文件/函数的职责。如果需要用"和""以及"来描述，说明职责过多。

这个原则适用于所有层级：

- **项目层级**：每个功能模块只负责一个业务领域
- **文件层级**：每个文件只负责一个功能单元
- **函数层级**：每个函数只做一件事
- **组件层级**：每个组件只负责一种 UI 展示或交互

> **示例——博客平台场景**："文章管理"模块只负责文章的增删改查和展示。如果把"用户评论"也塞进去，这个模块就同时管了两件事——改文章逻辑时可能不小心影响评论功能。正确做法是拆分为"文章管理"和"评论管理"两个模块。

#### 1.3 关注点分离

不同性质的代码应该分开存放，不要混在一起：

- UI 代码和业务逻辑分开
- 数据操作和数据展示分开
- 配置和实现分开
- 类型定义和运行逻辑分开

**为什么**：混在一起会导致修改一个功能需要同时改动多个不相关的部分。分开后每个部分可以独立修改、独立测试、独立复用。

> **类比**：好比一家餐厅——厨师负责做菜，服务员负责传菜，收银员负责结账。如果一个人同时干三件事，任何一个环节出问题都影响其他两个。

#### 1.4 显式优于隐式

代码应该清晰表达意图，不要依赖隐式行为：

- 明确的类型定义优于 any
- 明确的错误处理优于静默失败
- 明确的配置优于硬编码的魔法值
- 明确的函数名优于需要看实现才能理解的命名

| 做法 | 示例 |
|------|------|
| ❌ 不好 | `const rateLimit = 60` |
| ✅ 好 | `const API_RATE_LIMIT_PER_MINUTE = 60` |
| ❌ 不好 | `function process(d) { ... }` |
| ✅ 好 | `function processOrder(orderData: OrderInput): OrderResult { ... }` |

#### 1.5 渐进式复杂度

不要一开始就做最复杂的方案。先用最简单的方式跑通，遇到瓶颈再优化。

**实践含义**：

- 第一版不需要考虑所有边界情况
- 第一版不需要支持所有配置项
- 第一版不需要做完美的性能优化
- 但第一版的架构必须允许后续扩展

> **示例——电商后台场景**：第一版用一个页面展示所有订单，支持基本筛选。不需要一开始就做虚拟滚动、复杂排序、自定义列显示。但要预留：订单列表的接口设计应该能容纳未来的新筛选条件。

#### 1.6 一致性

同类操作的实现方式、代码风格、组织结构必须一致。一致性降低了认知负担——你和 AI 只需要理解一种模式，就能理解所有同类代码。

**实践含义**：

- 如果第一个 API 用 RESTful 风格，所有 API 都用
- 如果第一个组件用函数组件，所有组件都用
- 如果第一个模块的 hooks 放在 `hooks.ts`，所有模块都这样
- 如果第一个表的时间字段叫 `created_at`，所有表都这样

## 第二篇：项目架构

本篇讨论如何从零规划一个项目的代码组织。包括目录结构设计、模块划分、层级关系。

### 第二章：项目结构设计方法论

#### 2.1 两种组织方式

代码有两种基本组织方式：

**按技术角色组织（不推荐）：**

```
src/
├── components/     # 所有组件
├── hooks/          # 所有 hooks
├── services/       # 所有服务
├── types/          # 所有类型
├── utils/          # 所有工具
```

**问题**："修改订单功能"需要同时改动 `components/`、`hooks/`、`services/`、`types/` 中各一个文件。四个相关文件散落在四个目录中。功能越做越多后，每个目录都变成一个巨大的平铺列表。

**按功能模块组织（推荐）：**

```
src/
├── features/
│   ├── orders/       # 订单相关的一切
│   │   ├── components/
│   │   ├── hooks.ts
│   │   └── types.ts
│   ├── products/
│   └── users/
├── components/       # 跨模块共享的 UI 组件
├── lib/              # 跨模块共享的底层能力
└── types/            # 跨模块共享的类型
```

**优势**："修改订单功能"的所有相关代码都在 `features/orders/` 下。功能边界清晰，模块可以独立理解和修改。

#### 2.2 四层架构

推荐将代码分为四层，从上到下依赖：

| 层级 | 名称 | 职责 | 依赖 | 位置 |
|------|------|------|------|------|
| 第一层 | 页面层 | 具体页面和功能模块的实现 | 可以依赖下面所有层 | `src/features/`、`src/app/` |
| 第二层 | 组件层 | 可复用的 UI 组件 | 只依赖第四层 | `src/components/` |
| 第三层 | 业务层 | 业务逻辑、数据操作、外部 API 调用 | 只依赖第四层 | `src/lib/`、`src/services/` |
| 第四层 | 工具层 | 纯函数、类型定义、常量 | 不依赖任何其他层 | `src/utils/`、`src/types/` |

**依赖规则**：上层可以依赖下层，下层不能依赖上层。同层之间尽量不依赖，如需要则通过接口/类型解耦。

**违规示例**：

- `lib/` 中的文件 import 了 `components/` 中的组件 → 违规
- `utils/` 中的函数调用了 `services/` 中的 API → 违规
- `components/` 中直接调用了数据库操作 → 违规（应通过 hooks）

> **类比**：好比一栋楼——地基（工具层）承载墙体（业务层），墙体承载地板（组件层），地板承载房间里的家具（页面层）。你不能把家具放在地基下面。

#### 2.3 目录结构的决策框架

当不确定一个文件放在哪里时，按以下流程判断：

1. **这个文件是否只被一个功能模块使用？**
   - 是 → 放在该功能模块内部（`features/xxx/` 下）
   - 否 → 继续下一步
2. **这个文件是 UI 组件还是业务逻辑？**
   - UI 组件 → 放在 `components/` 下
   - 业务逻辑 → 放在 `lib/` 或 `services/` 下
3. **这个文件是否依赖 UI？**
   - 是（如包含 JSX）→ 放在 `components/` 下
   - 否（纯数据/逻辑）→ 放在 `lib/` 下
4. **这个文件是否是纯工具函数？**
   - 是 → 放在 `utils/` 下

#### 2.4 模块的内部结构

每个功能模块内部推荐的文件组织：

```
features/
├── module-name/
│   ├── index.ts           # 模块入口，导出公开接口
│   ├── PageComponent.tsx  # 页面级容器组件
│   ├── SubComponentA.tsx  # 子组件
│   ├── SubComponentB.tsx  # 子组件
│   ├── hooks.ts           # 本模块的 hooks（如果不超过 3 个）
│   ├── types.ts           # 本模块的类型定义
│   ├── constants.ts       # 本模块的常量
│   └── utils.ts           # 本模块的工具函数
```

如果模块内部有子功能需要进一步拆分：

```
features/
├── module-name/
│   ├── index.ts
│   ├── PageComponent.tsx
│   ├── sub-feature-a/     # 子功能目录
│   │   ├── ComponentA.tsx
│   │   └── hooks.ts
│   ├── sub-feature-b/
│   │   ├── ComponentB.tsx
│   │   └── hooks.ts
│   ├── types.ts
│   └── constants.ts
```

**规则**：

- 模块入口 `index.ts` 只做导出，不写业务逻辑
- 模块内部的实现细节不对外暴露，外部只能 import 模块的 `index.ts` 导出的内容
- 子功能目录不应超过 2 层嵌套

### 第二篇快速参考卡

**文件归属判断**：

1. 只被一个模块用？→ 放模块内
2. 是 UI 组件？→ `components/`
3. 是业务逻辑？→ `lib/`
4. 是纯工具？→ `utils/`

**依赖红线**：

- 下层不能 import 上层
- 同层不直接依赖，通过类型/接口解耦

**模块内部结构**：

`index.ts`（只导出）→ 页面组件 → 子组件 → `hooks.ts` → `types.ts`

## 第三篇：代码规范

本篇讨论代码层面的具体规范：文件怎么写、命名怎么定、类型怎么用、注释怎么加。

### 第三章：文件规范

#### 3.1 文件体积约束

**约束规则**：

- 单个源文件不超过 **300 行**（含注释和空行）
- 推荐控制在 **200 行以内**

**为什么是 300 行**：这不是一个精确的科学数字，而是一个经验阈值。300 行以内的文件，开发者可以在一次屏幕滚动中理解全貌。超过 300 行，阅读和定位问题的效率显著下降。在 AI 协作场景中，300 行以内的文件更可能被完整放入 AI 的上下文中。

**文件接近 300 行时的处理流程**：

1. 检查是否有独立的子组件可以抽取
2. 检查是否有业务逻辑可以提取到 `hooks` 或 `services`
3. 检查是否有工具函数可以提取到 `utils`
4. 如果拆分后每个文件都低于 200 行，说明拆分合理。如果拆分后出现了只有一二十行的"碎片"文件，说明过度拆分

**常见的文件膨胀原因及解决方案**：

| 原因 | 解决方案 |
|------|----------|
| 一个组件文件包含了所有子组件 | 每个子组件独立为一个文件，父组件只负责组装 |
| 一个文件包含了组件和业务逻辑 | 业务逻辑提取到 `hooks`，组件只负责渲染 |
| 一个文件包含了多种不相关的工具函数 | 按职责拆分到不同的工具文件中 |
| 一个文件包含了过多的样式定义 | 样式和组件分离，或使用 CSS Modules |

#### 3.2 文件命名规范

命名规则取决于文件内容的性质：

| 文件类型 | 命名风格 | 示例 |
|----------|----------|------|
| 组件文件（含 React/Vue 组件） | PascalCase | `OrderCard.tsx`、`SearchBox.tsx` |
| Hook 文件 | camelCase，`use` 前缀 | `useOrders.ts`、`useSelection.ts` |
| 工具/服务文件 | camelCase | `url.ts`、`date.ts`、`classifier.ts` |
| 类型定义文件 | camelCase | `order.ts`、`sync.ts`、`common.ts` |
| 常量文件 | camelCase | `constants.ts` |
| 测试文件 | 同名 + `.test`/`.spec` | `orders.test.ts`、`url.test.ts` |
| 配置文件 | 工具约定 | `tsconfig.json`、`vite.config.ts` |

#### 3.3 文件内容的排列顺序

一个文件内部的内容应该有固定的排列顺序。一致性让阅读者知道"在哪里找什么"。

**组件文件**：

1. import 语句（外部依赖 → 内部模块 → 类型 → 样式）
2. 类型定义（Props 等，如果只有本文件使用）
3. 常量定义
4. 辅助函数（纯函数，不依赖组件状态）
5. 组件定义
6. 导出

**Hook 文件**：

1. import 语句
2. 类型定义
3. Hook 函数定义
4. 导出

**工具/服务文件**：

1. import 语句
2. 类型定义
3. 常量定义
4. 函数定义（按调用关系或逻辑分组排列）
5. 导出

#### 3.4 import 顺序

所有文件的 import 语句按以下顺序排列，每组之间空一行：

```ts
// 第一组：外部依赖库
import React, { useState } from 'react'
import { useLiveQuery } from 'dexie-react-hooks'

// 第二组：内部共享组件
import { Button, Tag, Icon } from '@/components/ui'
import { Modal } from '@/components/layout'

// 第三组：内部业务模块
import { getOrders } from '@/lib/db/orders'
import { useOrders } from '@/hooks/useOrders'

// 第四组：类型导入
import type { Order, OrderFilter } from '@/types/order'

// 第五组：样式
import styles from './OrderList.module.css'
```

### 第四章：命名规范

#### 4.1 通用命名规则

| 类型 | 风格 | 示例 |
|------|------|------|
| 变量和函数 | camelCase | `orderCount`、`handleSelect`、`getOrders` |
| 类型和接口 | PascalCase | `Order`、`OrderFilter`、`SyncStatus` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT`、`SYNC_INTERVAL_MS` |
| 枚举值 | PascalCase 或 camelCase（项目内统一） | `SyncStatus.Synced` 或 `'synced'` |
| CSS 类名 | kebab-case 或 camelCase | `.order-card` 或 `styles.orderCard` |
| 文件夹名 | kebab-case | `order-detail`、`skill-api` |
| 环境变量 | UPPER_SNAKE_CASE | `VITE_API_BASE_URL` |

#### 4.2 命名的具体化程度

好的命名应该让读者不看实现就知道意图。

**变量命名**：

| 做法 | 示例 |
|------|------|
| ❌ 不好 | `data`、`list`、`item`、`temp`、`result` |
| ✅ 好 | `orders`、`pendingItems`、`selectedOrder`、`syncResult` |

**函数命名**：

| 做法 | 示例 |
|------|------|
| ❌ 不好 | `process`、`handle`、`do`、`make` |
| ✅ 好 | `fetchOrders`、`handleOrderSelect`、`createSyncJob`、`formatFileSize` |

**命名前缀约定**：

- 布尔变量用 `is`/`has`/`can`/`should` 前缀：`isLoading`、`hasError`、`canRetry`、`shouldRefresh`
- 事件处理函数用 `handle` 前缀：`handleClick`、`handleSubmit`、`handleOrderSelect`
- 回调函数用 `on` 前缀（用于 props）：`onClick`、`onSubmit`、`onSelect`

#### 4.3 避免的命名

| 避免 | 说明 | 建议 |
|------|------|------|
| 缩写 | `btn`、`txt`、`img`、`nav`、`cfg` | 用完整单词：`button`、`text`、`image`、`navigation`、`config`。例外：URL、API、ID、HTML 等通用缩写可以用 |
| 数字后缀 | `data1`、`data2`、`handler1` | 如果需要区分，说明结构需要重构 |
| 模糊泛化 | `utils.ts` 里面放了几十个互不相关的函数 | 按职责拆分：`url.ts`、`date.ts`、`format.ts` |

### 第五章：类型系统规范

#### 5.1 类型安全的必要性

在 AI 协作场景中，类型安全是最重要的防线之一。AI 可能写出逻辑正确但类型错误的代码，TypeScript 的类型检查能在编译阶段就发现问题，而不是等到运行时才报错。

> **类比**：类型定义就像是表格的表头——如果你不知道每一列该填什么，就可能把名字填到电话号码那一列。类型检查就是在提交表格之前自动帮你检查填错的地方。

#### 5.2 类型定义的位置

| 使用范围 | 放置位置 | 示例 |
|----------|----------|------|
| 仅在一个文件中使用 | 该文件的顶部（import 之后、组件/函数之前） | — |
| 一个模块内多文件共享 | 模块的 `types.ts` | `features/orders/types.ts` |
| 跨模块共享 | `src/types/` 目录 | `types/order.ts`、`types/sync.ts` |
| 与 API 响应对应 | API 相关模块 | `lib/api/types.ts` |

#### 5.3 类型定义规范

**规则 1：函数参数和返回值必须有类型**

```ts
// ❌ 不好
function getOrders(filter) { ... }

// ✅ 好
function getOrders(filter: OrderFilter): Promise<Order[]> { ... }
```

**规则 2：组件必须定义 Props 类型**

```ts
// ❌ 不好
function OrderCard({ title, price, status }) { ... }

// ✅ 好
interface OrderCardProps {
  title: string
  price: number
  status: OrderStatus
  variant?: 'compact' | 'detailed'
  onSelect?: (id: number) => void
}
function OrderCard({ title, price, status, variant = 'compact', onSelect }: OrderCardProps) { ... }
```

**规则 3：禁止使用 any**

除非确实无法确定类型且加了注释说明原因。绝大多数情况下都可以用 `unknown` 代替 `any`。`unknown` 是类型安全的"我不知道"，`any` 是类型不安全的"我不在乎"。

```ts
// ❌ 不好
const data: any = await fetch(...)

// ✅ 好
const data: unknown = await fetch(...)
// 后续通过类型守卫判断 data 的实际类型
```

**规则 4：使用 interface 还是 type**

- 用于对象结构的定义 → 用 `interface`（可以被 extends 和 implements）
- 用于联合类型、交叉类型、工具类型 → 用 `type`
- 项目内保持一致即可，不需要严格区分

**规则 5：API 响应必须有明确的类型**

```ts
// ❌ 不好
const response = await fetch(url)
const data = await response.json() // data 是 any

// ✅ 好
interface ApiResponse<T> {
  ok: boolean
  data: T
  error?: { code: string; message: string }
}
const response = await fetch(url)
const result: ApiResponse<Order[]> = await response.json()
```

#### 5.4 类型组织方式

按实体组织类型定义——实体类型和它的 Filter、Input 类型放在同一个文件中，相关的枚举类型也放在一起：

```ts
// types/order.ts
export interface Order {
  id: number
  productId: number
  quantity: number
  totalAmount: number
  status: OrderStatus
  customerName: string
  createdAt: string
  updatedAt: string
}

export type OrderStatus = 'pending' | 'processing' | 'shipped' | 'delivered' | 'cancelled'

export interface OrderFilter {
  status?: OrderStatus
  dateRange?: { start: string; end: string }
  search?: string
}

export interface CreateOrderInput {
  productId: number
  quantity: number
  customerName: string
}

export interface UpdateOrderInput {
  status?: OrderStatus
  quantity?: number
}
```

### 第六章：注释与文档规范

#### 6.1 注释原则

注释不是越多越好。好的代码应该尽量自解释，注释只在必要时添加。

**必须添加注释的情况**：

- 复杂的业务逻辑（解释"为什么这样做"，而非仅仅描述"做了什么"）
- 不直观的算法或计算
- 与外部系统的交互边界（API 调用、第三方库的特殊行为）
- 临时方案和 TODO 标记
- 绕过了某个限制的 hack（说明为什么需要 hack）

**不需要添加注释的情况**：

- 明显的操作（`const orders = await getOrders()`）
- 代码已经清楚表达的逻辑
- 函数的参数说明（类型定义已经说明了）

#### 6.2 注释格式

**行内注释**——用于解释单行或小段代码：

```ts
// 第三方 API 每分钟限 120 次，保守设为 60
const RATE_LIMIT = 60
```

**块注释**——用于解释复杂的逻辑段落：

```ts
/*
 * 订单同步引擎的冲突处理逻辑：
 * 当本地和远程都有修改时，以本地为准。
 * 但保留远程的版本信息，以便用户在冲突视图中查看差异。
 */
```

**TODO 注释**——标记待完成的工作：

```ts
// TODO: 实现订单的批量导出
// TODO(#issue-123): 修复大列表的滚动性能
```

**JSDoc 注释**——用于公共 API 的函数（特别是 `lib/` 层的函数）：

```ts
/**
 * 从数据库中获取订单列表
 * @param filter - 筛选条件
 * @returns 符合条件的订单数组
 */
export async function getOrders(filter?: OrderFilter): Promise<Order[]> { ... }
```

#### 6.3 项目上下文文件

这不是代码注释，而是一份专门给 AI 看的项目上下文文件。每次新对话开始时，把它给 AI 看，让 AI 快速理解项目背景。

```md
# 项目上下文

## 产品定位
[一句话描述]

## 技术栈
- 前端框架：[xxx]
- 类型检查：TypeScript
- 构建工具：Vite
- 本地数据库：[xxx]
- 样式方案：[xxx]

## 项目结构概要
[简要的目录树，不需要列出所有文件]

## 核心规范摘要
- 单文件不超过 300 行
- 新组件前检查组件清单
- 数据库变更前更新数据模型文档
- 所有变更记录到变更日志
- 不使用 any 类型
- 函数参数和返回值必须有类型定义

## 当前阶段
[当前在做什么里程碑，优先级是什么]

## 已有文档索引
- docs/COMPONENTS.md — 组件设计规范
- docs/DATA_MODEL.md — 数据模型规范
- docs/DEV_GUIDE.md — 开发工程规范
- docs/CHANGELOG.md — 变更日志
```

### 第三篇快速参考卡

**文件规范**：

- 单文件不超过 300 行（推荐 200 行以内）
- 组件用 PascalCase，hook 用 `useXxx`，其他用 camelCase
- import 顺序：外部 → 组件 → 业务 → 类型 → 样式

**命名规范**：

- 变量/函数：camelCase（如 `orderCount`）
- 类型/接口：PascalCase（如 `OrderFilter`）
- 常量：UPPER_SNAKE_CASE（如 `MAX_RETRY_COUNT`）
- 布尔变量：`is`/`has`/`can`/`should` 前缀

**类型安全**：

- 禁止 any（用 unknown 代替）
- 函数参数和返回值必须有类型
- 组件必须定义 Props 类型

**注释**：只在必要时添加——解释"为什么"而非"做了什么"。公共 API 用 JSDoc。

## 第四篇：依赖管理

本篇讨论如何选择、引入和管理第三方依赖。依赖是项目的"外部基因"——用得好是加速器，用不好是定时炸弹。

### 第七章：第三方依赖管理

#### 7.1 引入依赖的决策框架

在引入任何第三方依赖之前，先问三个问题：

1. **我真的需要这个依赖吗？** 先用原生方案尝试。很多时候自己写 20 行代码就能解决的问题，引入一个依赖反而增加了维护成本和安全风险。
2. **有没有更轻量的替代方案？** 同样功能的库可能有很多，优先选择体积最小的、维护最活跃的、依赖最少的。
3. **这个依赖会引入多少间接依赖？** 一个库可能依赖其他库，层层叠加后体积膨胀很快。安装前检查它的依赖树。

> **示例**：需求是在界面上显示一个日期选择器。❌ 引入一个 200KB 的完整 UI 组件库，只为了用它的日期选择器。✅ 找一个专门做日期选择的轻量库（可能只有 20KB）。

#### 7.2 评估标准

评估一个依赖时，看以下指标：

| 维度 | 关注点 |
|------|--------|
| 维护状态 | 最近一次更新是什么时候？开源 issue 有人回复吗？周下载量如何？ |
| 体积影响 | 安装后的磁盘大小、打包后对应用体积的影响 |
| 安全风险 | 已知漏洞数量、依赖的第三方库是否有安全问题 |
| 替代成本 | 如果以后要替换掉这个库，需要改多少地方？是直接调用还是深度集成？ |

#### 7.3 版本锁定与更新策略

**版本锁定**：

- `package.json` 中锁定精确版本（用 `^` 或 `~`）
- lock 文件（`package-lock.json` 或 `yarn.lock`）必须提交到版本控制
- 不要手动修改 lock 文件

**更新策略**：

- 不要盲目更新所有依赖
- 定期（每月或每季度）检查依赖更新
- 优先更新有安全补丁的依赖
- 更新前在测试环境验证

---

### 第四篇快速参考卡

**引入前检查**：

- [ ] 真的需要吗？原生方案能否解决？
- [ ] 最近有维护吗？（6 个月内有更新）
- [ ] 体积合理吗？（打包后 < 50KB 为佳）
- [ ] 有已知安全漏洞吗？
- [ ] 如果要替换，成本高吗？

**维护规则**：lock 文件必须提交 → 不盲目批量更新 → 优先更新安全补丁

## 第五篇：重构方法论

本篇讨论什么时候需要重构、怎么重构、如何控制重构风险。重构不是"推倒重来"，而是"在保持功能不变的前提下改善结构"。

### 第八章：重构方法论

#### 8.1 何时需要重构——识别重构信号

以下信号出现时，说明代码需要重构了：

| 信号 | 说明 |
|------|------|
| 修改一个功能需要改动 3 个以上不相关的文件 | 说明职责没有分离，或者耦合太严重 |
| 文件超过 300 行 | 说明职责过多，需要拆分 |
| 到处复制粘贴同样的逻辑 | 违反 DRY 原则，需要提取公共部分 |
| 修改代码时总是"小心翼翼"，担心改坏别的东西 | 说明模块边界不清，测试覆盖不够 |
| 同一个概念在代码中用了不同的名字 | 命名不一致，需要统一 |
| 加一个简单的功能需要改动很多地方 | 架构不够灵活，需要调整 |

#### 8.2 重构方案模板

重构前，先写清楚方案：

1. **当前问题**：描述具体问题，用"修改 XX 功能需要同时改 3 个文件"这样的表述
2. **重构目标**：重构后应该变成什么样
3. **影响范围**：列出所有需要改动的文件
4. **实施步骤**：分几步做，每步做什么
5. **验证方法**：重构后如何验证功能没有被破坏
6. **回滚方案**：如果重构出了问题，如何快速回滚

#### 8.3 重构的约束规则

- **规则 1：小步重构** —— 每次只改一个小问题，改完验证通过后再改下一个。不要一次性重构整个项目。
- **规则 2：功能与重构分离** —— 不要一边做新功能一边重构。重构和功能开发在不同的提交中。
- **规则 3：可验证** —— 重构后必须验证核心功能正常运行。最好有自动化测试，没有的话就手动走一遍核心流程。
- **规则 4：保留原有行为** —— 重构只改内部结构，不改外部行为。用户看到的界面、操作流程应该和重构前完全一样。

#### 8.4 与 AI 协作重构的约束

当让 AI 重构代码时，必须明确约束：

1. 明确说"只重构结构，不改功能"
2. 要求 AI 每次只改一个小问题
3. 每次改动后立即运行测试验证
4. 不允许 AI "顺手"优化不相关的地方
5. 如果 AI 建议大幅重构，要求先说明理由和风险

---

### 第五篇快速参考卡

**重构信号**：

- [ ] 改一个功能要改 3+ 个文件
- [ ] 文件超过 300 行
- [ ] 到处复制粘贴
- [ ] 改代码时"小心翼翼"
- [ ] 同一概念多个名字
- [ ] 加简单功能要改很多地方

**重构步骤**：写方案（问题→目标→影响→步骤→验证→回滚）→ 小步执行 → 每步验证 → 功能和重构分开提交

**AI 约束**：只重构结构，不允许"顺手"优化不相关的地方

## 第六篇：版本管理与发布

本篇讨论 Git 分支策略、提交信息规范、版本号规则。版本管理是项目的"时间机器"——出问题时能回滚，要发布时有章法。

### 第九章：Git 与发布

#### 9.1 简化分支策略

个人项目不需要复杂的分支模型。简化方案：

```
main               ← 生产环境，始终可运行
├── feat/order-export  ← 开发订单导出功能
├── fix/date-format    ← 修复日期格式问题
└── refactor/db-layer  ← 重构数据库层
```

**规则**：

- `main` 分支永远保持可运行状态
- 不直接在 `main` 上改代码
- 功能分支开发完成后先合并到 `main`，再删除功能分支

#### 9.2 提交信息规范

使用 Conventional Commits 格式：

```
<type>(<scope>): <description>
```

| type | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(order): 添加订单导出为 CSV 功能` |
| `fix` | 修复 bug | `fix(auth): 修复 token 过期后无法刷新的问题` |
| `refactor` | 重构（不改功能） | `refactor(db): 将查询逻辑从组件提取到 service 层` |
| `docs` | 文档更新 | `docs: 更新项目 README` |
| `style` | 样式调整 | `style: 统一按钮圆角为 8px` |
| `test` | 测试相关 | `test: 添加订单模块单元测试` |
| `chore` | 构建/工具变更 | `chore: 升级 Vite 到 5.x` |

#### 9.3 版本号规则

使用 Semantic Versioning（语义化版本）：

```
major.minor.patch
 1.  0.  0
```

| 位置 | 含义 | 示例 |
|------|------|------|
| major | 不兼容的 API 变更 | 数据库结构完全重设计，旧数据需要迁移 |
| minor | 向后兼容的新功能 | 添加订单导出功能 |
| patch | 向后兼容的问题修复 | 修复日期显示为 UTC 时间的问题 |

#### 9.4 变更日志

维护一份 `CHANGELOG.md`，记录每个版本的变更：

```md
# 变更日志

## [1.1.0] - 2026-08-21

### 新增
- 订单导出为 CSV 功能
- 订单列表支持按日期筛选

### 修复
- 修复日期显示为 UTC 时间的问题

### 变更
- 订单列表默认每页显示 20 条

## [1.0.1] - 2026-08-15

### 修复
- 修复登录页面样式错乱问题
```

| 维度 | 规范 |
|------|------|
| Git 分支 | `main` 始终可运行，不直接改；每个里程碑/功能开分支，完成后合并 |
