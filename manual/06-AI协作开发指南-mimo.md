# AI 协作开发指南

- **日期**：2026-08-21
- **版本**：v1.0
- **适用范围**：适用于个人开发者与 AI 协作开发中小型软件项目的完整流程指导。本文覆盖协作流程、沟通技巧、偏差处理、上下文管理、约束规则和行为准则，以 Web 应用为主要场景，但方法论不限于特定技术栈。示例使用通用场景（博客平台、电商后台等），不绑定特定项目。

---

## 第一篇：协作流程

本篇定义人与 AI 协作开发的完整流程框架。六阶段模型是项目从想法到上线的主干路径，每个阶段有明确的目标、产出物和准入条件。

### 第一章：六阶段开发框架

#### 1.1 阶段概览

| 阶段 | 名称 | 目标 | 核心产出物 | 参与者 |
|------|------|------|------------|--------|
| P1 | 需求讨论 | 将模糊想法整理为结构化需求 | 需求总纲、决策锁定清单 | 人（主导）+ AI（辅助整理） |
| P2 | 原型设计 | 确定界面布局和交互方式 | 页面原型、视觉设计规范 | 人（主导）+ AI（辅助生成） |
| P3 | 技术设计 | 确定技术方案和架构 | 技术方案确认书、数据模型设计 | 人（确认）+ AI（主导设计） |
| P4 | 文档编写 | 产出开发所需的全部文档 | API 清单、组件清单、开发里程碑 | 人（审核）+ AI（主导编写） |
| P5 | 开发实现 | 按模块逐个实现功能 | 可运行的功能模块 | 人（审查）+ AI（主导编码） |
| P6 | 测试部署 | 验证功能并上线 | 上线系统、迭代需求清单 | 人（验收）+ AI（辅助修复） |

#### 1.2 阶段详细说明

##### P1：需求讨论

**阶段目标**：将模糊的产品想法转化为结构化、无歧义的需求描述。明确"做什么"和"不做什么"。

**核心活动**：

1. 描述产品愿景和目标用户
2. AI 追问细节，整理出功能清单
3. 划定"不做清单"，明确边界
4. 定义 MVP（最小可行产品）范围
5. 逐一确认关键决策（技术选型方向、数据存储方式等）

**产出物清单**：

- 需求总纲（功能列表 + 优先级 + 异常场景）
- 决策锁定清单（已确认的关键决策记录）
- 不做清单（明确排除的功能范围）

**阶段闸门**（进入 P2 的条件）：

- [ ] 需求总纲已确认，没有悬而未决的功能点
- [ ] 决策锁定清单中所有项目已由人确认
- [ ] 不做清单已明确定义

**AI 在该阶段的角色**：追问者和整理者。AI 负责把零散的想法整理成结构化文档，追问遗漏的场景，但不做最终决策。

> **示例——博客平台场景**：你说"我想做一个博客平台"，AI 会追问：是否支持多作者？是否需要评论功能？文章是否支持 Markdown？你逐一回答后，AI 整理成需求总纲。你确认后进入 P2。

---

##### P2：原型设计

**阶段目标**：确定界面的布局、交互流程和视觉风格。让人在写代码之前就能"看到"最终产品的大致样子。

**核心活动**：

1. 确定页面清单（有哪些页面）
2. 确定页面布局和导航结构
3. 定义关键交互流程（如"发布文章"的步骤）
4. 确定视觉风格（配色、字体、间距等基础规范）

**产出物清单**：

- 页面原型（每个页面的线框图或低保真原型）
- 视觉设计规范（色彩、字体、间距等基础定义）
- 页面清单（页面名称 + 功能说明）

**阶段闸门**（进入 P3 的条件）：

- [ ] 所有页面的布局已确认
- [ ] 核心交互流程已确认
- [ ] 视觉风格方向已确定

**AI 在该阶段的角色**：执行者和建议者。人确定设计方向，AI 生成原型草图和设计规范文档。AI 可以提出交互建议，但人做最终决定。

---

##### P3：技术设计

**阶段目标**：将产品需求和技术原型转化为可执行的技术方案。确定数据模型、模块划分、技术栈选型。

**核心活动**：

1. 确定技术栈（框架、语言、构建工具）
2. 设计数据模型（实体、关系、字段）
3. 划分功能模块（哪些模块、模块边界）
4. 设计模块间的通信方式（API 设计、事件机制等）
5. 确定部署方案

**产出物清单**：

- 技术方案确认书（技术栈 + 架构方案 + 部署方案）
- 数据模型设计（实体定义 + 字段说明 + 关系图）
- 模块划分方案（模块列表 + 模块职责 + 模块边界）

**阶段闸门**（进入 P4 的条件）：

- [ ] 技术栈已确认，且标记为"已确认，不可更改"
- [ ] 数据模型已确认，没有悬而未决的字段
- [ ] 模块划分已确认，每个模块的职责明确

**AI 在该阶段的角色**：方案设计者。AI 基于需求和原型产出技术方案，人负责审核和确认。关键决策（如技术栈选择）必须由人确认。

---

##### P4：文档编写

**阶段目标**：将技术设计细化为开发阶段可以直接参考的详细文档。AI 在编码前先产出文档，人确认后再进入编码。

**核心活动**：

1. 编写 API 接口清单（每个接口的路径、参数、返回值）
2. 编写组件清单（每个组件的职责、Props、使用场景）
3. 编写开发里程碑（按模块排列的开发顺序和预估时间）
4. 编写数据模型的详细字段说明

**产出物清单**：

- API 接口清单
- 组件清单
- 开发里程碑（模块开发顺序 + 完成标准）
- 数据模型详细文档

**阶段闸门**（进入 P5 的条件）：

- [ ] 所有 API 接口已定义，参数和返回值明确
- [ ] 组件清单已确认，职责边界清晰
- [ ] 开发里程碑已排列，优先级已确认

**AI 在该阶段的角色**：文档编写者。AI 基于 P3 的技术设计产出详细文档，人负责审核准确性。文档是后续编码的"合同"。

---

##### P5：开发实现

**阶段目标**：按里程碑顺序逐个实现功能模块。每个模块完成后验证通过，再进入下一个。

**核心活动**：

1. 按里程碑顺序逐个模块实现
2. 每个模块实现后运行测试验证
3. 记录变更日志
4. 遇到问题时回溯文档，确认是需求遗漏还是实现偏差

**产出物清单**：

- 可运行的功能模块（按里程碑逐个交付）
- 变更日志（记录每次变更的内容和原因）

**阶段闸门**（进入 P6 的条件）：

- [ ] 所有里程碑模块已实现
- [ ] 核心功能流程可正常运行
- [ ] 变更日志已更新

**AI 在该阶段的角色**：编码执行者。AI 按文档编写代码，人负责审查代码质量和功能正确性。AI 不得在未经确认的情况下修改架构或添加文档中未定义的功能。

---

##### P6：测试部署

**阶段目标**：验证所有功能正常，修复发现的问题，完成部署上线。

**核心活动**：

1. 全流程功能测试
2. 修复测试中发现的 bug
3. 性能检查和优化
4. 部署上线
5. 记录迭代需求清单（后续可以改进的点）

**产出物清单**：

- 上线系统
- 迭代需求清单（测试和使用中发现的改进点）
- 部署文档（如果部署流程有变化）

**阶段闸门**（项目完成的条件）：

- [ ] 所有核心功能测试通过
- [ ] 无严重 bug 遗留
- [ ] 系统可正常访问和使用

**AI 在该阶段的角色**：修复者和优化者。AI 帮助定位和修复 bug，优化性能，但不做架构级的改动。

---

│                    六阶段开发框架                             │

│                                                             │

│  │需求讨论│  确认需求  │原型设计│  确认原型  │技术设计│          │
│  └──────┘           └──────┘           └──────┘          │
│                                                      │          │
│                                               闸门    │          │
│                                          确认技术方案  │          │
│                                                      ↓          │
│  ┌──────┐    闸门    ┌──────┐    闸门    ┌──────┐          │
│  │  P6  │←───────────│  P5  │←───────────│  P4  │          │
│  │测试部署│  模块完成  │开发实现│  文档确认  │文档编写│          │
│  └──────┘           └──────┘           └──────┘          │
│                                                             │
└─────────────────────────────────────────────────────────────┘

阶段推进规则：
  P1 → P2：需求总纲 + 决策锁定清单 已确认
  P2 → P3：页面原型 + 视觉规范 已确认
  P3 → P4：技术方案 + 数据模型 已确认
  P4 → P5：API 清单 + 组件清单 + 里程碑 已确认
  P5 → P6：所有模块已实现且核心流程可运行
  P6 → 完成：所有核心功能测试通过
```

#### 1.4 不可跳过的原则

**原则 1：不确认不进入下一阶段**

每个阶段的闸门条件必须满足后才能进入下一阶段。AI 不得以"先做着，后面再改"为由跳过确认环节。

**原则 2：不超范围改动**

在 P5 开发实现阶段，只做里程碑中定义的功能。发现新的需求或改进点，记入"后续迭代清单"，不在当前模块中实现。

**原则 3：不绕过文档直接编码**

P4 的文档是 P5 编码的依据。AI 不得在文档未确认的情况下开始写代码。如果发现文档有遗漏，先补充文档，确认后再编码。

## 第二篇：沟通技巧

本篇讨论人与 AI 协作时的沟通方法。好的沟通能减少返工，提高协作效率。核心原则是：每次对话要有明确的议题、充分的上下文、清晰的边界。

### 第二章：有效沟通方法论

#### 2.1 方案先行原则

在让 AI 动手写代码之前，先讨论方案。方案讨论的目的是确认方向正确，避免方向性返工。

**为什么重要**：AI 可以很快写出大量代码，但如果方向错了，推倒重来的成本远高于花 10 分钟讨论方案。

**实践方法**：

| 场景 | 做法 |
|------|------|
| 新功能开发 | 先说"我要做 XX 功能，请先给我方案，不要写代码" |
| 代码重构 | 先说"请分析当前代码的问题，给出重构方案，不要直接改" |
| 技术选型 | 先说"请比较 A 和 B 两种方案的优劣，列出对比表，我来选" |
| Bug 修复 | 先说"请先分析可能的原因，列出排查方向，再动手修" |

> **示例——电商后台场景**：你要给订单列表加筛选功能。❌ 直接说"给订单列表加筛选"——AI 可能会做出一个你不想要的复杂筛选器。✅ 先说"我要给订单列表加筛选功能，请先讨论方案：筛选条件有哪些？交互方式是顶部筛选栏还是侧边栏？筛选结果是实时更新还是点击查询？"

#### 2.2 上下文提供

每次对话开始时，提供充分的项目背景信息。AI 没有跨会话的记忆，每次新对话都是一张白纸。

**必须提供的信息**：

1. **项目名称和当前阶段**：让 AI 知道自己在做什么项目、做到哪一步了
2. **当前讨论的具体文件**：告诉 AI 你在看哪个文件，让 AI 也去看
3. **技术约束**：框架版本、语言版本、已确定的技术栈
4. **已有规范**：项目的编码规范、命名约定、架构约束
5. **已做的决策**：哪些技术决策已经确定，不可更改

**提供的格式**：

```markdown
## 项目上下文
- 项目：XX 电商平台，当前处于 P5 开发阶段
- 技术栈：React + TypeScript + Vite + SQLite
- 当前任务：实现订单列表的筛选功能
- 相关文件：src/features/orders/ 目录下的所有文件
- 约束：不要修改数据模型，不要引入新的第三方依赖
- 参考：请先阅读 docs/API.md 了解已定义的接口
```

#### 2.3 范围限制

每次对话只讨论一个明确的议题。话题发散是 AI 协作中最常见的效率杀手。

**为什么重要**：AI 的上下文窗口有限，话题发散会导致上下文稀释，AI 在后半段对话中更容易犯错或遗忘前面的约定。

**实践方法**：

- 一次只实现一个功能点
- 一次只修改一个模块
- 一次只讨论一个技术问题
- 如果发现需要改动多个地方，拆分为多次对话

**话题发散的信号**：

| 信号 | 说明 | 处理方式 |
|------|------|----------|
| 对话中出现了 3 个以上不相关的文件 | 话题已经偏离 | 停下来，重新聚焦 |
| AI 开始修改你没有提到的文件 | 范围失控 | 立即制止，要求回退 |
| 讨论了超过 30 分钟还没有结论 | 方向不明 | 停下来，重新定义议题 |

#### 2.4 分步确认

每个关键决策点停下来确认，不要一口气让 AI 做完整个项目。

**需要停下来的时刻**：

1. AI 给出了方案，确认方案再动手
2. AI 完成了一个模块，检查后再做下一个
3. AI 提出了技术建议，确认再采纳
4. 遇到文档中未定义的情况，确认再处理

**确认的格式**：

```markdown
请确认以下内容：
1. 数据模型方面：你打算加一个 XX 字段，类型是 XX，是否正确？
2. 接口方面：你会新增一个 XX 接口，参数是 XX，返回值是 XX，是否正确？
3. 组件方面：你会创建 XX 组件，职责是 XX，是否正确？
请逐一确认或纠正。
```

#### 2.5 问题描述格式

向 AI 描述问题时，使用统一的格式，确保信息完整、无歧义。

**问题描述模板**：

```markdown
## 问题描述

### 现象
[具体表现，什么操作触发、看到什么结果]

### 预期
[应该是什么样的结果]

### 已尝试
[已经尝试过的解决方法和结果]

### 环境信息
- 文件：[相关文件路径]
- 技术栈：[使用的框架/库版本]
- 复现步骤：[1. 2. 3.]
```

> **示例——博客平台场景**：
> ```markdown
> ## 问题描述
>
> ### 现象
> 在文章编辑页面点击"保存"按钮后，页面没有反应，控制台报错：
> "TypeError: Cannot read property 'title' of undefined"
>
> ### 预期
> 点击保存后，文章内容应该被保存，页面显示"保存成功"提示
>
> ### 已尝试
> 检查了数据库，数据没有写入。检查了 API 接口，接口没有被调用。
> 怀疑是前端调用 API 之前的参数组装有问题。
>
> ### 环境信息
> - 文件：src/features/articles/components/ArticleEditor.tsx
> - 技术栈：React 18 + TypeScript + Vite
> - 复现步骤：1. 打开文章编辑页  2. 修改标题  3. 点击保存
> ```

- [ ] 每次对话是否只讨论一个明确的议题？
- [ ] 关键决策点是否停下来确认了？
- [ ] 问题描述是否包含：现象 + 预期 + 已尝试 + 环境信息？
- [ ] 是否避免了话题发散（一次只改一个地方）？

## 第三篇：偏差处理

本篇讨论 AI 在协作过程中可能出现的偏差类型、识别方法和纠正策略。偏差是 AI 协作的常态，关键是能快速识别并纠正。

### 第三章：AI 偏差的识别与纠正

#### 3.1 偏差类型分类

| 偏差类型 | 定义 | 严重程度 | 典型后果 |
|----------|------|----------|----------|
| 方向性偏差 | AI 理解错了需求，做的东西不是你要的 | 高 | 大量返工，浪费时间 |
| 结构性偏差 | AI 违反了项目架构规范，破坏了模块边界 | 高 | 后续维护困难，连锁反应 |
| 质量性偏差 | AI 产出的代码质量不达标（命名差、缺少类型、逻辑混乱） | 中 | 代码可维护性下降 |
| 上下文偏差 | AI 忘记了之前的约定，在新对话中重复犯错 | 中 | 重复修复，效率低下 |

#### 3.2 各类偏差的识别信号

##### 方向性偏差的识别信号

- AI 实现的功能和你描述的需求不一致
- AI 做了你没提到的功能，漏掉了你要求的功能
- AI 的实现方式和你预期的交互流程不同
- 代码能运行，但结果不是你想要的

> **示例**：你要求"文章列表按时间倒序排列"，AI 做了一个"文章列表按分类分组展示"——这是方向性偏差。AI 可能把"分类"和"排序"混淆了。

##### 结构性偏差的识别信号

- AI 在不该耦合的模块之间建立了依赖
- AI 把业务逻辑写在了 UI 组件里
- AI 新建了不在项目架构中的目录结构
- AI 引入了不在技术栈中的库或工具
- AI 修改了本不应该修改的共享模块

> **示例**：你让 AI 在订单模块加一个功能，AI 顺手改了用户模块的代码——这是结构性偏差。订单模块不应该直接修改用户模块。

##### 质量性偏差的识别信号

- AI 使用了 any 类型
- AI 没有给函数参数和返回值加类型
- AI 的变量命名模糊（如用 `data`、`temp`、`result`）
- AI 的函数超过 50 行且没有拆分
- AI 复制粘贴了重复逻辑而没有提取公共部分
- AI 没有处理错误情况（缺少 try-catch 或错误状态处理）

##### 上下文偏差的识别信号

- AI 在新对话中重新引入了之前已经排除的方案
- AI 忘记了项目的技术约束（如禁止使用某个库）
- AI 在新对话中违反了之前确认的命名约定
- AI 重复犯了之前已经纠正过的错误

> **示例**：你在上一个对话中告诉 AI"不要用 any 类型"，新对话中 AI 又开始用 any——这是上下文偏差。

#### 3.3 纠正方法

##### 方向性偏差的纠正

**步骤**：

1. 立即停止 AI 的当前操作
2. 明确指出偏差："你做的 XX 和我要求的 XX 不一致"
3. 重新描述需求，用更具体的语言
4. 如果需求本身有歧义，先澄清需求再让 AI 重新做

**话术模板**：

```markdown
等一下，这和我要求的不一致。

我要求的是：[用一句话重新描述需求]
你做的是：[指出实际做了什么]

区别在于：[说明差异点]

请按照我的要求重新实现，不要改动其他代码。
```

> **示例**：
> ```markdown
> 等一下，这和我要求的不一致。
>
> 我要求的是：文章列表按创建时间倒序排列
> 你做的是：文章列表按分类分组展示
>
> 区别在于：我不要分组，只要按时间排序
>
> 请按照我的要求重新实现，不要改动其他代码。
> ```

##### 结构性偏差的纠正

**步骤**：

1. 立即停止 AI 的当前操作
2. 明确指出违反了哪个架构约束
3. 要求 AI 回退对非目标模块的修改
4. 重新描述任务，强调边界

**话术模板**：

```markdown
停一下，你修改了不应该修改的文件。

任务范围是：[只修改 XX 模块]
你额外修改了：[列出不该改的文件]

请：
1. 回退对 [非目标文件] 的修改
2. 只在 [目标模块] 内完成任务
3. 不要建立跨模块的新依赖
```

> **示例**：
> ```markdown
> 停一下，你修改了不应该修改的文件。
>
> 任务范围是：只在 orders 模块内添加筛选功能
> 你额外修改了：src/features/users/hooks.ts
>
> 请：
> 1. 回退对 users 模块的修改
> 2. 只在 orders 模块内完成任务
> 3. 不要建立 orders 和 users 之间的新依赖
> ```

##### 质量性偏差的纠正

**步骤**：

1. 指出具体的质量问题
2. 引用项目规范中的相关条款
3. 要求 AI 按规范修正
4. 检查修正结果

**话术模板**：

```markdown
这段代码有几个质量问题：

1. [具体问题 1] —— 这违反了项目规范中关于 [规范条款] 的要求
2. [具体问题 2] —— 请参考项目中 [已有文件名] 的写法

请按以下要求修正：
- [修正要求 1]
- [修正要求 2]
```

> **示例**：
> ```markdown
> 这段代码有几个质量问题：
>
> 1. 使用了 any 类型 —— 这违反了项目规范中关于"禁止使用 any"的要求
> 2. 函数名用了 process —— 应该更具体，如 processOrder
> 3. 没有处理 API 调用失败的情况 —— 请参考 src/features/products/hooks.ts 的错误处理写法
>
> 请按以下要求修正：
> - 用 unknown 或具体类型代替 any
> - 函数名改为描述性名称
> - 添加 try-catch 错误处理
> ```

##### 上下文偏差的纠正

**步骤**：

1. 在新对话开始时，明确提供项目上下文和约束
2. 如果 AI 重复犯错，更强调约束条件
3. 考虑将关键约束写入 PROJECT_CONTEXT.md 文件

**话术模板**：

```markdown
请注意以下项目约束（之前已经确认过的）：

1. [约束 1]
2. [约束 2]
3. [约束 3]

这些约束在之前的对话中已经确认，请严格遵守。
```

#### 3.4 偏差处理流程图

```
┌────────────────────────────────────────────────────────┐
│                   偏差处理流程                          │
├────────────────────────────────────────────────────────┤
│                                                        │
│  发现异常                                              │
│     │                                                  │
│     ↓                                                  │
│  判断偏差类型                                          │
│     │                                                  │
│  ┌──┴──────────┬──────────────┬──────────────┐        │
│  ↓              ↓              ↓              ↓        │
│ 方向性偏差    结构性偏差    质量性偏差    上下文偏差    │
│  │              │              │              │        │
│  ↓              ↓              ↓              ↓        │
│ 停止操作      停止操作      指出问题      强调约束      │
│ 重新描述      回退修改      引用规范      补充上下文    │
│ 需求          明确边界      要求修正      写入文件      │

│         └──────┬───────┴──────────────┘                │

#### 3.5 偏差的预防

偏差的预防比纠正更重要。以下措施可以减少偏差发生的概率：

1. **充分的上下文**：每次对话开始时提供完整的项目背景
2. **明确的约束**：在 PROJECT_CONTEXT.md 中列出所有关键约束
3. **方案先行**：先讨论方案再动手，方向性偏差在方案阶段就能发现
4. **分步确认**：每完成一步就检查，偏差在早期更容易纠正
5. **引用已有代码**：让 AI 参考项目中已有的写法，减少质量性偏差

## 第四篇：上下文管理

本篇讨论如何在对话内外管理 AI 的上下文。AI 没有跨会话的持久记忆，上下文管理是确保 AI 持续产出正确结果的关键能力。

### 第四章：会话与上下文策略

#### 4.1 PROJECT_CONTEXT.md 的使用

PROJECT_CONTEXT.md 是项目的"AI 上下文文件"，记录了 AI 需要知道的关键信息。每次新对话开始时，让 AI 先读取这个文件。

**什么时候更新**：

| 触发条件 | 更新内容 |
|----------|----------|
| 完成了一个新模块 | 补充模块的目录结构和关键实现方式 |
| 做了新的技术决策 | 补充决策内容和原因 |
| 发现了 AI 常犯的错误 | 补充"常见陷阱"部分 |
| 技术栈有变化 | 更新技术栈信息 |
| 新增了重要约束 | 补充约束条件 |

**更新什么内容**：

```markdown
# 项目上下文

## 产品定位
[一句话描述项目是做什么的]

## 技术栈
- 前端框架：[xxx + 版本]
- 类型检查：TypeScript
- 构建工具：[xxx]
- 数据存储：[xxx]
- 样式方案：[xxx]

## 项目结构概要
[简要的目录树，列出主要模块]

## 核心规范摘要
- 单文件不超过 300 行
- 禁止使用 any 类型
- 新组件前检查组件清单
- 所有变更记录到变更日志
- 数据库变更前更新数据模型文档

## 当前阶段
[当前在做什么里程碑，优先级是什么]

## 已完成的模块
[列出已完成的模块和它们的位置]

## 当前约束
[列出当前阶段必须遵守的约束条件]

## 常见陷阱
[列出 AI 在本项目中容易犯的错误]

## 已有文档索引
- docs/xxx.md — [说明]
```

**如何在新对话中使用**：

```markdown
请先阅读 PROJECT_CONTEXT.md 了解项目背景和当前状态。
本次对话的任务是：[具体任务描述]
```

#### 4.2 会话策略

**何时开新对话**：

| 场景 | 选择 |
|------|------|
| 完成了一个模块，要开始下一个 | 开新对话 |
| 话题完全切换（从开发切到测试） | 开新对话 |
| 当前对话已经很长（超过 50 轮） | 开新对话 |
| 当前对话出现了明显的上下文偏差 | 开新对话 |
| 要处理一个独立的 bug 修复 | 开新对话 |

**何时继续当前对话**：

| 场景 | 选择 |
|------|------|
| 同一个功能还没做完 | 继续当前对话 |
| 需要对刚才的改动做小幅调整 | 继续当前对话 |
| 发现了相关问题需要一起处理 | 继续当前对话 |

**会话长度建议**：

- 简单任务：单次对话完成即可
- 中等任务（一个功能模块）：1-2 次对话
- 复杂任务（多个模块联动）：拆分为多次对话，每次聚焦一个模块
- 单次对话建议不超过 50 轮交互

#### 4.3 大任务拆分

将大任务拆分为适合单次对话的小任务，是提高 AI 协作效率的关键。

**拆分原则**：

1. **按模块拆分**：每个模块是一个独立的对话任务
2. **按层次拆分**：先做数据层，再做业务层，最后做 UI 层
3. **按依赖拆分**：被依赖的模块先做，依赖其他模块的后做

**拆分格式**：

```markdown
## 任务拆分

### 任务 1：数据层（数据模型 + 数据库操作）
- 创建数据模型类型定义
- 实现数据的增删改查函数
- 完成标准：所有数据操作函数可正常调用

### 任务 2：业务层（业务逻辑 + 状态管理）
- 实现订单筛选的业务逻辑
- 创建管理状态的 hooks
- 完成标准：业务逻辑可正确处理各种筛选条件

### 任务 3：UI 层（组件 + 页面）
- 实现筛选条件选择组件
- 实现订单列表展示组件
- 连接业务层和 UI 层
- 完成标准：用户可以通过界面完成筛选操作
```

#### 4.4 上下文传递

在对话之间传递关键信息，确保新对话的 AI 能延续之前的工作。

**传递方法**：

1. **PROJECT_CONTEXT.md**：记录项目级别的上下文（见 4.1）
2. **变更日志**：记录每次变更的内容和原因
3. **代码注释**：在关键代码处留下上下文注释
4. **对话摘要**：新对话开始时，用一段话总结上一次对话的成果和遗留问题

**对话摘要模板**：

```markdown
## 上次对话摘要
- 完成了：[具体完成了什么]
- 遗留问题：[还有什么没做完的]
- 关键决策：[做了什么技术决策，原因是什么]
- 注意事项：[下次对话需要注意什么]
```

## 第五篇：约束规则汇总

本篇汇总 AI 在协作开发中必须遵守的约束规则。这些规则来自工程实践，目的是确保 AI 产出的代码符合项目规范。

### 第五章：AI 协作约束清单

#### 5.1 工程约束

| 编号 | 约束 | 说明 |
|------|------|------|
| E1 | 单文件不超过 300 行 | 超过时必须拆分，推荐控制在 200 行以内 |
| E2 | 禁止使用 any 类型 | 用 unknown 或具体类型代替 |
| E3 | 函数参数和返回值必须有类型 | 任何新增或修改的函数都要有完整类型 |
| E4 | 组件必须定义 Props 类型 | 使用 interface 定义 |
| E5 | import 顺序固定 | 外部 → 组件 → 业务 → 类型 → 样式 |
| E6 | 命名遵循项目约定 | 组件 PascalCase，hook 用 use 前缀，其他 camelCase |
| E7 | 不引入未经确认的第三方依赖 | 引入前必须讨论必要性和替代方案 |
| E8 | 不修改文档中未定义的文件 | 只改任务范围内指定的文件 |
| E9 | 每次变更记录到变更日志 | 记录变更内容和原因 |
| E10 | 新模块前检查已有模块 | 避免重复创建功能相似的模块 |

#### 5.2 组件约束

| 编号 | 约束 | 说明 |
|------|------|------|
| C1 | 新组件前先检查组件清单 | 确认没有可复用的现有组件 |
| C2 | 组件只负责一种 UI 展示或交互 | 职责不清晰时拆分为子组件 |
| C3 | 组件文件只包含 UI 相关代码 | 业务逻辑放在 hooks 或 services 中 |
| C4 | 组件 Props 使用 interface 定义 | 不使用内联类型 |
| C5 | 可选 Props 必须有默认值 | 在解构时给出默认值 |
| C6 | 组件导出使用命名导出 | 不使用 default export |
| C7 | 共享组件放在 components 目录 | 模块专用组件放在模块内部 |

#### 5.3 数据库约束

| 编号 | 约束 | 说明 |
|------|------|------|
| D1 | 数据库变更前更新数据模型文档 | 先改文档，再改代码 |
| D2 | 每个表有 id、created_at、updated_at | 统一的时间戳字段 |
| D3 | 字段名使用 snake_case | 与数据库惯例一致 |
| D4 | 新增字段不能破坏已有数据 | 必须有默认值或允许 null |
| D5 | 删除字段前确认无代码引用 | 全局搜索确认后再删除 |
| D6 | 数据库操作封装在专门的数据层 | UI 组件不直接操作数据库 |

#### 5.4 安全约束

| 编号 | 约束 | 说明 |
|------|------|------|
| S1 | 不在代码中硬编码密钥或密码 | 使用环境变量或配置文件 |
| S2 | 用户输入必须经过验证和清理 | 前后端都要验证 |
| S3 | API 接口需要权限验证 | 根据接口敏感度确定验证级别 |
| S4 | 不在日志中输出敏感信息 | 密码、token、个人信息等 |
| S5 | SQL 操作使用参数化查询 | 禁止字符串拼接 SQL |
| S6 | 文件上传需要类型和大小限制 | 防止恶意文件上传 |

#### 5.5 测试约束

| 编号 | 约束 | 说明 |
|------|------|------|
| T1 | 测试文件与源文件同名 + .test 后缀 | 位置与源文件相邻或在 __tests__ 目录 |
| T2 | 每个测试用例只测一个行为 | 一个 test 函数验证一个断言点 |
| T3 | 测试命名描述被测行为 | 如 "should return empty array when no orders match filter" |
| T4 | 测试不依赖外部服务 | 使用 mock 或 stub |
| T5 | 测试覆盖核心业务逻辑 | 数据操作、业务规则、边界情况 |
| T6 | 修复 bug 时补充回归测试 | 确保同样的问题不会再出现 |

#### 5.6 重构约束

| 编号 | 约束 | 说明 |
|------|------|------|
| R1 | 重构只改结构，不改功能 | 外部行为必须和重构前完全一致 |
| R2 | 小步重构，逐步推进 | 每次只改一个小问题 |
| R3 | 重构前先写方案 | 方案经确认后再动手 |
| R4 | 重构和功能开发分离 | 不在同一个提交中混入重构和新功能 |
| R5 | 重构后立即验证 | 运行测试或手动走核心流程 |
| R6 | 保留回滚能力 | 确保能快速回退到重构前的状态 |

#### 5.7 约束的执行方式

**如何让 AI 遵守约束**：

1. **在 PROJECT_CONTEXT.md 中列出核心约束**：AI 每次新对话都会读取
2. **在任务描述中强调相关约束**：如"请注意禁止使用 any 类型"
3. **在审查代码时逐条检查**：对照约束清单检查 AI 的产出
4. **发现违反时立即纠正**：引用约束编号，要求修正

**约束冲突时的处理优先级**：

1. 安全约束（最高优先级）
2. 数据库约束
3. 工程约束
4. 组件约束
5. 测试约束
6. 重构约束

## 第六篇：行为准则

本篇定义 AI 在协作开发中的行为边界。AI 不只是一个代码生成工具，它应该有自己的判断力——知道什么时候该做、什么时候该问、什么时候该拒绝。

### 第六章：AI 自主性规范

#### 6.1 预见优于补救

在写代码之前，先判断潜在风险。AI 应该在动手之前预判可能的问题，而不是等问题出现后再修复。

**AI 应该在动手前思考的问题**：

1. 这个改动会影响哪些其他模块？
2. 有没有已有的代码可以复用？
3. 这个实现方式是否有已知的陷阱？
4. 修改这个文件是否会影响正在运行的功能？

**实践方式**：

```markdown
在开始实现之前，我先分析一下：

1. 影响范围：这个改动只影响 [目标模块]，不会影响其他模块
2. 复用检查：[已有组件/函数] 可以复用，不需要重新实现
3. 风险评估：这个实现方式有一个潜在风险 [xxx]，我的应对方案是 [xxx]
4. 是否需要确认：[某个决策] 需要你确认后才能继续

确认以上分析没问题后，我开始实现。
```

#### 6.2 强制确认机制

以下决策必须获得用户确认后才能执行，AI 不得自行决定：

| 决策类型 | 必须确认的原因 |
|----------|----------------|
| 技术栈选择 | 影响整个项目的方向 |
| 数据模型变更 | 影响所有依赖该数据的模块 |
| 引入新的第三方依赖 | 增加项目复杂度和维护成本 |
| 修改非任务范围内的文件 | 可能影响其他功能 |
| 删除文件或数据 | 不可逆操作 |
| 修改共享组件 | 影响所有使用该组件的模块 |
| 修改安全相关代码 | 可能引入安全漏洞 |
| 架构层面的调整 | 影响后续所有开发 |

**AI 在遇到以上情况时的标准话术**：

```markdown
⚠️ 需要确认

我打算 [描述操作]，这属于需要确认的操作，原因如下：
- [为什么需要确认]
- [这个操作的影响范围]
- [可能的风险]

是否确认执行？
```

#### 6.3 主动补位

发现遗漏或风险时主动提示，不要等用户发现后再被动回应。

**AI 应该主动提示的场景**：

| 场景 | 提示内容 |
|------|----------|
| 发现文档中未定义的情况 | "这个情况在文档中没有定义，建议先确认处理方式" |
| 发现潜在的性能问题 | "这个实现在数据量大时可能有性能问题，建议 [优化方案]" |
| 发现已有代码可以复用 | "项目中已有 [组件/函数]，功能类似，建议复用而非重新实现" |
| 发现约束可能被违反 | "这个操作可能违反 [约束条款]，建议 [替代方案]" |
| 发现不一致的命名或风格 | "项目中已有 [文件] 用了不同的命名方式，建议统一为 [方式]" |

**主动提示的标准格式**：

```markdown
💡 建议

在实现过程中发现一个情况：[描述发现]

建议处理方式：[具体建议]
原因：[为什么这样建议]

是否采纳？
```

#### 6.4 拒绝有害请求

AI 有权拒绝可能导致数据丢失、安全漏洞、严重违反工程规范的请求。

**必须拒绝的请求类型**：

| 请求类型 | 拒绝理由 |
|----------|----------|
| 硬编码数据库密码或 API 密钥 | 安全风险 |
| 禁用所有安全验证 | 安全风险 |
| 使用 DROP TABLE 删除整个表 | 数据丢失风险 |
| 批量修改而不先备份 | 数据丢失风险 |
| 在生产环境中执行未经测试的代码 | 稳定性风险 |
| 绕过类型检查使用大量 any | 代码质量风险 |

**拒绝的标准话术**：

```markdown
⚠️ 无法执行此操作

这个请求可能导致 [具体风险]。

建议的替代方案：
1. [替代方案 1]
2. [替代方案 2]

请确认你想要的处理方式。
```

> **示例**：
> ```markdown
> ⚠️ 无法执行此操作
>
> 你要求删除 orders 表中的所有数据，这会导致所有订单记录永久丢失。
>
> 建议的替代方案：
> 1. 如果是测试数据，只删除特定测试账号的数据
> 2. 如果是重置，先导出备份再删除
> 3. 使用软删除（标记为已删除）而非物理删除
>
> 请确认你想要的处理方式。
> ```

#### 6.5 保持上下文一致

复用现有组件和工具，遵循已有规范。AI 不应该在已有方案的情况下重新发明轮子。

**一致性检查清单**：

1. 实现新功能前，检查项目中是否有类似功能可以复用
2. 命名新变量前，检查项目中同类变量的命名方式
3. 写新函数前，检查项目中是否有功能相似的函数
4. 创建新组件前，检查组件清单中是否有可复用的组件
5. 选择实现方式前，检查项目中同类问题的已有解法

**一致性标准格式**：

```markdown
一致性检查：

1. 复用检查：项目中已有 [xxx]，可以复用
2. 命名一致性：同类变量在项目中统一使用 [xxx] 命名方式
3. 风格一致性：参考 [xxx 文件] 的实现风格
```

#### 6.6 非技术用户沟通标准

当用户不熟悉技术术语时，AI 应该使用通俗语言解释技术概念，说明决策的实际影响，给出明确的推荐选项。

**沟通原则**：

1. **首次使用术语时解释**：不要假设用户理解所有技术术语
2. **说明实际影响**：用"这会导致 XX"而非仅说"这在技术上更好"
3. **给出推荐选项**：不要只列选项不推荐，用户需要的是决策支持
4. **量化影响**：尽可能用数字说明（如"这会让页面加载快 2 秒"）

**术语解释的标准格式**：

```markdown
这里用到了 [术语]，简单解释一下：
- 它是什么：[一句话解释]
- 在我们的项目中意味着：[具体影响]
- 我的建议是：[推荐选项]，因为 [原因]
```

> **示例**：
> ```markdown> 这里涉及"缓存"的概念，简单解释一下：
> - 它是什么：把数据暂时存在一个快速读取的地方，下次需要时直接取，不用重新计算
> - 在我们的项目中意味着：用户打开文章列表时，第一次会慢一点，之后会很快
> - 我的建议是：先做缓存，因为文章列表是高频访问的页面，缓存效果明显
> ```

- [ ] 结构性偏差要求回退对非目标模块的修改

- [ ] AI 遵守重构约束（只改结构不改功能、小步推进）
