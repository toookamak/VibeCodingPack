# 需求分析

- **日期**：2026-08-21
- **版本**：v1.0
- **适用范围**：适用于个人开发者与 AI 协作的中小型项目，以 Web 应用为主要场景，但方法论不限于特定技术栈。本文使用通用场景示例，不绑定特定项目。

---

## 第一篇：方法论

在讨论具体做法之前，先建立需求分析的方法论。需求分析决定了项目"做什么"和"不做什么"，是所有后续工作的输入。输入错了，后面的架构设计、编码实现做得再好，也是在错误的方向上加速。

### 第一章：需求分析的目标与原则

#### 1.1 需求分析解决什么问题

需求分析的任务，是把"我想要一个 XX"这样的模糊想法，变成人和 AI 都能照着执行的结构化描述。

跳过需求分析直接开写的典型后果：

| 跳过环节 | 直接后果 | 修复成本 |
|----------|----------|----------|
| 没澄清目标 | 做出来的功能不是真正想要的，整体方向偏移 | 推倒重来 |
| 没定义验收标准 | "做完了"但不知道好不好用，反复调整 | 反复返工 |
| 没划清边界 | 功能越加越多，项目永远做不完 | 无限期延期 |
| 没考虑异常场景 | 上线后遇到边界情况频繁打补丁 | 持续还债 |

修改成本随阶段推进快速放大。同一个需求的变更，在需求阶段改一句话即可，在开发阶段可能要改数据模型和接口，上线后则涉及用户数据和兼容性：

```
需求阶段        设计阶段        开发阶段        上线后
  改一句话  →   改一页方案  →   改多个模块  →   改代码+数据+用户沟通
 （分钟级）      （小时级）       （天级）         （周级）
```

> **结论**：个人开发者最容易犯的错误不是"不会分析需求"，而是"觉得项目小不用分析"。项目越小，越没有余量承受返工——需求分析恰恰是小项目的性价比之王。

#### 1.2 需求的三个层次

一个完整的需求描述分三层。讨论需求时先上层后下层，避免直接扎进功能细节：

| 层次 | 回答的问题 | 示例（博客平台） |
|------|-----------|------------------|
| 业务需求 | 为什么做？达成什么目的？ | 沉淀技术文章，建立个人影响力 |
| 用户需求 | 谁在什么场景下用它解决什么问题？ | 读者能快速找到感兴趣的文章；作者能低门槛发布 |
| 功能需求 | 具体做什么？ | 支持 Markdown 写作、标签分类、按标签筛选文章 |

**常见错误**：从功能需求开始聊（"我要加个搜索""我要做个看板"），跳过前两层。结果是功能越堆越多，却说不清哪个功能服务于哪个目标。发现自己在聊功能时，先退一步问："这个功能支撑了哪条用户需求？"

#### 1.3 四条核心原则

**先问题后方案**

讨论需求时只谈"要解决什么问题"，不谈"用什么技术怎么实现"。方案属于 P3 技术设计阶段（见 06-AI协作开发指南）。过早进入方案讨论有两个害处：一是被实现难度带偏，把"该不该做"偷换成"好不好做"；二是锁死思路，错过更简单的解法。

> **示例——电商后台场景**：需求是"运营人员需要知道哪些商品卖得好"。如果直接进方案，可能讨论出一张复杂的数据报表页；退回问题层面，答案可能只是"商品列表按销量排序列出前 20"——一行 SQL 加一个排序参数就解决了。

**可验证**

每条需求都要能回答"怎么判断它做成了"。不可验证的需求（"界面要友好""性能要好"）无法验收，也无法拆解为里程碑。写不出来验收标准的"需求"，通常还没想清楚。

**记录决策**

比"决定做什么"更重要的是记录"为什么这么决定"。决策理由是后续争议时的裁判依据：三周后你忘了为什么砍掉某个功能时，决策记录能防止反复摇摆。已确认的决策记入决策锁定清单，未确认的记入待讨论事项（见第四章）。

**划清边界**

"不做什么"和"做什么"同等重要。不做清单（明确排除的功能范围）有三个作用：防止范围蔓延、给 AI 划定发挥边界、减少未来"要不要顺手做了"的心理内耗。

### 第二章：需求收集与澄清

方法论确定后，进入具体操作。本篇讨论需求从哪里来、如何把模糊表述澄清为可执行的需求条目。

### 第二章引导之外的话：收集和澄清是一件事的两面

收集是把散落各处的需求素材聚拢；澄清是把每条素材追问到可验证为止。两者交替进行，不必严格分先后。

#### 2.1 需求从哪里来

| 来源 | 举例 | 注意点 |
|------|------|--------|
| 自己的痛点 | 手动整理书签太麻烦 | 最可靠的来源，但容易高估普遍性 |
| 对现有工具的不满 | 现有笔记工具同步慢 | 先确认不满的是核心流程还是边缘体验 |
| 他人的抱怨 | 朋友抱怨记账麻烦 | 区分"抱怨"和"愿意换工具" |
| 竞品参考 | 某产品有个好用的功能 | 只借鉴思路，警惕照抄功能清单 |
| 灵感闪现 | "要是能自动 XX 就好了" | 先记下来放进待讨论清单，不当场拍板 |

个人开发者的特殊性：自己既是需求方又是开发者，省去了用户调研环节，但也失去了"外部视角"的保护。对策是把想法先写成文字放一天，第二天再读——经不起重读的需求多半站不住。

#### 2.2 五问澄清法

对每条模糊需求，依次过五个问题：

1. **问题**——它要解决什么问题？（回到业务需求层）
2. **用户**——谁在什么场景下使用？使用频率多高？
3. **现状**——现在是怎么解决的？具体不满在哪？
4. **标准**——做到什么程度算成功？如何验证？
5. **边界**——哪些情况明确不需要覆盖？

> **示例——博客平台场景**：原始需求是"我想给博客加个搜索"。五问展开：
>
> 1. 问题：读者找不到几个月前写过的一篇文章。
> 2. 用户：读者在浏览博客时使用；博主自己也用来找旧文。频率：每天数次到每周几次。
> 3. 现状：靠浏览器 Ctrl+F，只能搜当前页；文章多了以后基本失效。
> 4. 标准：输入关键词，1 秒内返回标题和正文匹配的文章列表。
> 5. 边界：第一版不做全文检索的分词优化、不做搜索建议、不做热门搜索词统计。
>
> 五问之后，这条需求从"加个搜索"变成了可估算、可验收的功能点。

五问不必每次全部机械走完，但第 4 问（标准）和第 5 问（边界）永远不能省。

#### 2.3 用户故事与验收标准

澄清后的需求用用户故事格式记录：

```
作为 <角色>，我想要 <功能>，以便 <价值>。
```

每条用户故事附验收标准。两种写法任选：

**Checklist 式**（适合简单功能）：

```markdown
US-3 作为读者，我想要按标签筛选文章，以便快速找到同主题内容。

验收标准：
- [ ] 文章列表页可按单个标签筛选
- [ ] 筛选结果只包含含该标签的文章
- [ ] 清除筛选后恢复全量列表
```

**Given-When-Then 式**（适合有状态流转的功能）：

```markdown
US-7 作为作者，我想要保存文章草稿，以便中途离开后继续编辑。

验收标准：
Given 正在编辑一篇未发布的文章
When 点击"保存草稿"
Then 文章以草稿状态保存，列表中标记为"草稿"

Given 文章已是草稿状态
When 再次点击"保存草稿"
Then 更新原草稿内容，不产生重复草稿
```

**❌/✅ 对比**：

| 写法 | 问题/优点 |
|------|-----------|
| ❌ "支持草稿功能" | 无法验收：什么叫支持？自动还是手动？存几份？ |
| ✅ 用户故事 + 验收标准 | 边界清晰，可直接转化为测试用例和里程碑功能点 |

#### 2.4 异常场景补充

正常流程只是需求的一部分。大量返工来自"没想到的异常"。逐项过以下检查清单，为每个功能补齐异常场景：

| 异常类型 | 提问模板 | 示例（文章发布） |
|----------|----------|------------------|
| 空状态 | 数据为空时显示什么？ | 还没写过文章时，列表页显示什么？ |
| 操作失败 | 失败时用户看到什么？数据会丢吗？ | 保存失败时，正在编辑的内容是否保留？ |
| 极端数据 | 超长、超多、为空、特殊字符？ | 标题 1000 字、正文 10 万字时表现如何？ |
| 重复提交 | 用户连点两次会怎样？ | 快速双击"发布"会不会发出两篇？ |
| 权限不足 | 未登录/无权限时呢？ | 访问他人草稿链接时显示什么？ |
| 中断恢复 | 做到一半断了怎么办？ | 编辑到一半浏览器崩溃，内容还在吗？ |

不是每个功能都要覆盖全部六类。判断标准：这个异常发生时，用户会遭遇不可逆损失或强烈困惑吗？会，就必须定义行为；不会，可以留到后续迭代。

### 第三章：需求整理与决策

收集和澄清产出一堆零散的需求条目，本篇讨论如何分类、排序、划定范围，形成可进入下一阶段的决策结果。

#### 3.1 需求分类

所有需求条目归入三类：

| 类别 | 内容 | 常见遗漏 |
|------|------|----------|
| 功能需求 | 系统要做的事情（用户故事为主） | — |
| 非功能需求 | 做到什么质量：性能、安全、可用性、兼容性 | 几乎总是被遗漏 |
| 约束 | 既定条件：技术栈、时间预算、运行环境、个人能力边界 | 与非功能需求混淆 |

**非功能需求参考基线**（中小型 Web 项目适用，按需增删）：

- 页面首屏加载不超过 2 秒（常规网络环境）
- API 平均响应不超过 300ms，P95 不超过 1 秒
- 所有用户输入在前后端双重校验
- 密码哈希存储，敏感配置不入库不入仓
- 移动端浏览器可完成核心流程（如适用）

**约束示例**：单人开发、业余时间每周约 10 小时、部署预算每月 0～5 美元、技术栈限定为团队熟悉的 React + Node.js。约束不满足时要砍需求，而不是硬扛约束。

#### 3.2 冲突识别

需求之间、需求与约束之间经常打架。显式暴露冲突，比开发到一半才发现要好得多。

| 冲突类型 | 示例 | 处理方式 |
|----------|------|----------|
| 需求 vs 需求 | "一键导出全部数据" vs "私密内容严格隔离" | 定义例外规则：导出时排除私密内容并提示 |
| 需求 vs 约束 | "实时协同编辑" vs "单人业余开发、零服务器预算" | 降低目标：改为"最后写入胜出 + 版本历史" |
| 需求 vs 技术现实 | "完全离线可用" vs "多端数据强一致" | 明确取舍优先级：本地优先，接受短暂不一致 |

处理冲突的四步：**暴露冲突 → 评估各方代价 → 人拍板 → 记录决策及理由**。AI 可以协助列出冲突和代价，但取舍必须由人决定（见第六章）。

#### 3.3 优先级排序

用三级优先级标记每条需求：

| 级别 | 含义 | 判据 |
|------|------|------|
| P0 必须 | 没有它产品不能用 | 缺了它，核心场景跑不通 |
| P1 应该 | 没有它明显难用 | 核心场景能跑通，但用户会抱怨 |
| P2 可以 | 有了更好 | 锦上添花，不影响可用性 |

两条经验规则：

- **P0 占比超过总量的 40%，说明没想清楚**——多数"必须"其实是"应该"。强制自己重新排序。
- **P0 是 MVP 的候选集，但不等于 MVP**——MVP 还要结合依赖关系裁剪（见 3.4）。

优先级排序完成后，这些需求条目将作为 11-开发里程碑计划中"列功能、定核心"两步的直接输入。

#### 3.4 MVP 与不做清单

**MVP（最小可行产品）**：能用最小功能集跑通核心场景的版本。定义 MVP 的句式：

> 用户可以用 [P0 功能的最小组合]，完整地走通 [核心场景]。

> **示例——博客平台场景**：MVP = 作者能创建和发布 Markdown 文章，读者能浏览文章列表和阅读详情。评论、标签、搜索、主题美化都不是 MVP——它们让博客更好用，但"写"和"读"已经成立。

**不做清单**：明确写出本期不做的事项及原因：

```markdown
## 不做清单（v1 范围外）

| 事项 | 原因 | 重启条件 |
|------|------|----------|
| 多作者协作 | 个人博客，无此场景 | 出现真实多人写作需求 |
| 评论系统 | 需要反垃圾投入，偏离核心 | 有稳定读者群后再议 |
| 全文检索引擎 | 文章量 < 200 篇，LIKE 查询够用 | 文章量超过 500 篇 |
| 移动端 App | 响应式 Web 已覆盖 | Web 版移动端留存数据证明必要 |
```

不做清单里的"重启条件"很关键——它把"永远不做"和"现在不做"区分开，避免误杀有潜力的方向。

#### 3.5 需求评审闸门

进入原型设计（P2）之前，逐项检查：

- [ ] 每条需求都能追溯到业务需求和用户需求
- [ ] 每条需求都有验收标准
- [ ] 高风险功能已补齐异常场景（空状态、失败、极端数据至少想过一遍）
- [ ] 非功能需求和约束已显式列出
- [ ] 已知冲突全部有了裁决和记录
- [ ] P0/P1/P2 已标注，P0 占比不超过 40%
- [ ] MVP 范围和不做清单已确认
- [ ] 待讨论事项清单中，没有阻塞 MVP 的悬而未决项

任何一项不满足，先补齐再进入下一阶段。这就是 06-AI协作开发指南中 P1 阶段闸门的具体化。

## 第二篇：产出物

方法论和澄清技巧最终要落成文档。文档不是负担，而是新对话中给 AI 的上下文、三周后自己的记忆备份。

### 第四章：需求说明书写作规范

#### 4.1 文档定位

需求说明书是需求分析阶段的核心交付物，对应 06-AI协作开发指南 P1 阶段产出的完整文档形态：需求总纲（功能列表 + 优先级 + 异常场景）、决策锁定清单、不做清单三者合并在一份文档中。

`examples/dogear/01-需求说明书.md` 是一份完整的实战实例，可与本章模板对照阅读。

#### 4.2 模板结构

```markdown
# [项目名] 需求说明书

> **版本**: v0.1.0
> **日期**: [日期]
> **状态**: 草稿 / 评审中 / 已确认
> **更新记录**: 见文末版本记录

# 01. 产品定义
   定位（一句话说清是什么）、核心理念（关键取舍）、目标用户

# 02. 用户需求与核心工作流
   原始需求整理（保留提出顺序）、痛点描述、核心工作流

# 03. 产品整体架构
   系统组成示意、数据流向（粗粒度，不等于技术设计）

# 04. 核心功能设计
   逐个功能模块：用户故事 + 验收标准 + 异常场景 + 优先级

# 05. 安全与约束
   操作边界、兜底机制、非功能需求基线、既定约束

# 06. 部署与运行环境
   部署形态预期、访问方式（可暂定）

# 07. 阶段规划
   Phase 1 / Phase 2 / Phase 3 的范围划分

# 08. 待讨论事项
   悬而未决的问题清单（编号 + 问题 + 状态）

# 09. 术语表
   项目内自定义术语的解释

# 附录：版本记录
   版本、日期、变更内容
```

#### 4.3 各章写作要点

| 章节 | 写作要点 | 常见坑 |
|------|----------|--------|
| 产品定义 | 定位一句话不超过 40 字；理念写取舍而非口号 | 写成宣传文案；堆砌形容词 |
| 用户需求 | 保留原始表述再附结构化整理，原始记录是澄清依据 | 只留结论，丢失上下文 |
| 整体架构 | 画组成和数据流即可，不写技术选型细节 | 越界写成技术设计文档 |
| 核心功能 | 每个功能独立小节，故事 + 标准 + 异常齐全 | 大段散文式描述，无法验收 |
| 安全与约束 | AI 操作边界、软删除等兜底机制在此定义 | 完全遗漏，开发时临时补 |
| 阶段规划 | Phase 1 必须是完整闭环，后续是增强 | Phase 1 塞太多，迟迟见不到可运行成果 |
| 待讨论事项 | 每条有编号和状态，定期清账 | 只增不减，变成垃圾抽屉 |

#### 4.4 精简示例——博客平台场景

以下是一个刻意精简的示例，展示关键章节的最小合格形态：

```markdown
# 简博 需求说明书

> **版本**: v0.1.0　**日期**: 2026-08-21　**状态**: 评审中

# 01. 产品定义

定位：面向个人作者的极简 Markdown 博客系统。
核心理念：写作和阅读体验优先，社交功能一律不做。
目标用户：有 Markdown 写作习惯的个人开发者。

# 04. 核心功能设计（节选）

## 4.1 文章管理（P0）
```

#### 4.5 常见错误

| 错误 | 表现 | 后果 |
|------|------|------|
| 把方案当需求写 | 通篇是"用什么框架、建什么表" | 需求没定就锁死实现，方案错了连需求一起返工 |
| 只写正常流程 | 每个功能只有 happy path | 开发中不断被异常情况打断 |
| 全部标 P0 | 20 个功能 18 个"必须" | 没有裁剪依据，里程碑排不出来 |

| 文档写完即冻结 | 需求变更后文档不更新 | 文档失去信任，AI 和人都开始凭记忆干活 |

### 第五章：需求变更管理

需求会变，这是常态。变更管理的目标不是阻止变化，而是让变化受控、可追溯。

#### 5.1 变更处理流程

```
提出变更
   │
   ▼
┌──────────────┐    否    ┌──────────────────┐
│ 影响评估      │────────→│ 记入待讨论事项     │
│ 范围/工作量/  │          │ （择期再议）       │
│ 已开发部分    │          └──────────────────┘
└──────┬───────┘
       │ 是
       ▼
┌──────────────┐
│ 人拍板        │  接受 / 推迟 / 拒绝，记录理由
└──────┬───────┘
       │ 接受
       ▼
更新需求说明书 → 同步联动文档 → 记入版本记录
```

**影响评估三问**：影响哪些已完成的功能？增加多少工作量？是否动摇已锁定的决策？

**分级处理**：

- **小变更**（改文案、调交互细节、补异常分支）：直接更新文档，记入版本记录即可。
- **大变更**（新增功能模块、改变核心流程、推翻已锁定决策）：必须走完整流程，且评估是否需要调整里程碑计划（见 11-开发里程碑计划 2.4 节）。

#### 5.2 版本记录规范

需求说明书文末维护版本记录表：

| 版本 | 日期 | 变更内容 | 影响 |
|------|------|----------|------|
| v0.1.0 | 2026-08-21 | 初始版本 | — |
| v0.2.0 | 2026-09-02 | 新增标签维度；整理模式改为两阶段分拣 | Phase 1 工期 +3 天；MILESTONES.md 已同步 |

约定：新增功能块升次版本号（v0.x），文字修订升修订号（v0.x.y）；状态从"草稿"变"已确认"时记录一次。

#### 5.3 变更后的文档联动

需求变更不是改一份文档就结束。按变更类型同步联动：

| 变更类型 | 必须同步更新的文档 |
|----------|--------------------|
| 新增/删除功能 | `docs/MILESTONES.md`、`docs/API.md`、`docs/DATA_MODEL.md`（涉及时） |
| 调整 MVP 或阶段划分 | `PROJECT_CONTEXT.md`（当前阶段）、`docs/MILESTONES.md` |
| 非功能需求变化 | `docs/DESIGN.md` |
| 新增术语 | 需求说明书术语表、`PROJECT_CONTEXT.md` |

联动检查可纳入 12-健康检查清单的例行检查，避免文档间悄悄失配。

## 第三篇：AI 协作

需求分析是人机协作收益最高的阶段之一——AI 读得多、记得全、不知疲倦地追问，恰好补上个人开发者最大的短板：盲区。

### 第六章：与 AI 协作做需求分析

#### 6.1 分工原则

一条铁律：**人定方向，AI 补盲区**。

| 适合交给 AI | 必须人来做 |
|-------------|------------|
| 追问遗漏的场景和边界 | 判断问题是否值得解决 |
| 把口语化描述整理成结构化条目 | 确定优先级和取舍 |
| 找出需求之间的矛盾 | 裁决冲突 |
| 为每个功能生成异常场景候选清单 | 确认哪些异常需要覆盖 |
| 检查验收标准是否可验证 | 最终确认需求说明书 |

AI 在 P1 阶段的角色是"追问者和整理者"（见 06-AI协作开发指南 1.2 节），不是决策者。

#### 6.2 需求澄清提示词模板

```markdown
## 角色
你是需求分析助手。当前处于需求讨论阶段（P1），禁止讨论技术实现。

## 任务
我正在构思一个项目，需要你帮我澄清需求。

## 我的想法
[粘贴你的原始想法，允许口语化、碎片化]

## 你的工作方式
1. 先用五问法逐条追问：解决什么问题、谁在什么场景用、
   现状如何、成功标准、明确不做什么
2. 每轮最多提 5 个问题，等我回答后再继续
3. 我回答含糊时追问，不要自行脑补默认值
4. 发现需求之间的矛盾时立即指出
5. 不要夸我，不要迎合，发现伪需求直接说出来

## 输出要求
澄清完成后，输出：
1. 结构化需求清单（用户故事 + 验收标准 + 优先级建议）
2. 异常场景清单（按功能分组）
3. 你认为我想清楚了/没想清楚的点，各列一节
4. 待讨论事项清单
```

模板要点：**禁止讨论技术实现**（防跑偏）、**限制每轮提问数**（防轰炸）、**要求指出没想清楚的点**（防迎合）。

#### 6.3 AI 常见问题防范

| 问题 | 表现 | 防范手段 |
|------|------|----------|
| 迎合式确认 | 你提什么都回"好的，没问题"，从不质疑 | 提示词中明确要求找反例、提质疑；主动问"这个想法最大的问题是什么" |
| 过度设计 | 给简单需求配企业级方案（微服务、消息队列） | 声明项目规模和约束；要求"先给最简可行版" |
| 提前跳到方案 | 还没澄清"做什么"就开始写技术选型 | 在任务中显式声明当前阶段和禁区（P1 不谈实现） |
| 遗漏边界 | 只整理正常流程 | 用 2.4 节的六类异常清单让 AI 逐个功能过一遍 |
| 脑补默认值 | 你没说的细节它替你定了 | 要求 AI 把所有假设单独列出，逐条向你确认 |

最后一条例行化：每次 AI 输出需求整理结果，都追加一句"列出你做出的全部假设"——假设清单是最容易被忽略的需求漏洞来源。

#### 6.4 阶段衔接

P1 通过评审闸门后，向下一阶段交接的材料包：

1. **需求说明书**（已确认状态）——P2 原型设计的直接输入（原型怎么做，见 05-用户体验设计指南）
2. **决策锁定清单**——后续所有阶段的决策依据
3. **不做清单**——给 P2~P6 各阶段的 AI 划定发挥边界

开启新对话时，按 06-AI协作开发指南第四篇的方式提供上下文：需求说明书 + PROJECT_CONTEXT.md，而不是整份粘贴历史聊天记录。

## 快速参考卡

**四条核心原则**：

- [ ] 先问题后方案（P1 不谈技术实现）
- [ ] 可验证（每条需求有验收标准）
- [ ] 记录决策（理由比结论重要）
- [ ] 划清边界（不做清单与做什么同等重要）

**五问澄清法**：

- [ ] 解决什么问题？
- [ ] 谁在什么场景下用？
- [ ] 现在怎么解决的？
- [ ] 做到什么程度算成功？
- [ ] 明确不包含什么？

**异常场景六类**：

- [ ] 空状态　[ ] 操作失败　[ ] 极端数据
- [ ] 重复提交　[ ] 权限不足　[ ] 中断恢复

**需求分类与排序**：

- [ ] 功能需求 / 非功能需求 / 约束 三类齐全
- [ ] P0 占比不超过 40%
- [ ] MVP = P0 的最小闭环组合
- [ ] 不做清单带重启条件

**评审闸门（进入 P2 前）**：

- [ ] 需求可追溯、可验证、异常场景已补
- [ ] 冲突已有裁决记录
- [ ] MVP 与不做清单已确认
- [ ] 无阻塞 MVP 的待讨论事项

**AI 协作防范**：

- [ ] 声明阶段禁区（P1 不谈实现）
- [ ] 要求质疑而非迎合
- [ ] 索取假设清单并逐条确认
- [ ] 人负责所有取舍和拍板

**变更管理**：

- [ ] 小变更直接改文档，大变更走影响评估
- [ ] 每次变更记入版本记录
- [ ] 按 5.3 节表格同步联动文档
